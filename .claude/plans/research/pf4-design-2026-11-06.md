# PF-4 design panel (2026-11-06) — read-only, 3 designs + 2 judges

Source: workflow run wf_079017d8-e1d. Nothing in this file is measured; every ns figure is Assumed until a bench runs.

## Judgment

**Winner:** Design 2, "PF-4 risk-first: stage typed rows on the drain, encode on the writer and rescue threads". It is used as the base, with grafts from designs 1 and 3 (see synthesis).

**Scores:**

Scores are out of 10. Order of columns: correctness (zero loss, byte-identical rows) / hot-path cost / diff size (higher = smaller and safer) / testability / weighted total (correctness counted double).

D1, minimal-change, TickRecord holding TickRow, labels snapshotted at hand-off: 6.5 / 8 / 8.5 / 8 / 7.5.
D2, risk-first, StagedRow with per-batch label pins, accounting unchanged: 9 / 7.5 / 6.5 / 9 / 8.2. WINNER.
D3, performance-first, 80 B wire-image record, ParsedTick conversion moved to the writer: 7.5 / 9.5 / 5.5 / 8 / 7.6.

Claims I checked against the code (Verified):

- `TickRow` is 264 B. Its fields: i64 id 8, `&'static str` segment 16, four 8 B scalars, five `Option<f64>`, eight `Option<i64>` (tick_persistence.rs:576-616). D1's and D2's size figures are right, and the plan's "~200 B" is wrong.
- `write_tick_line_columns` (tick_persistence.rs:491) and `append_aux_row` (feed_aux_persistence.rs:335) each call `candle_contract_labels()` (an ArcSwap `LABELS.load()`, candle_contract_labels.rs:140) once per row. So moving the encode to the writer changes which label table a row reads unless something pins it. All three designs correctly found this.
- `append_tick_into` builds the row first, then runs the band check, then the window check, then the quotes route. The ledger `note_row_appended` and `tick_ts_placement::note_row` run only after an `Ok` append (lines 2938-3110). The failure arm calls `note_unapplied`, `append_dropped` and a power-of-two `HotPath02` log, and the aux arm has the same handling of its own (3217-3260). All three designs keep these on the drain at the same points.
- `from_parsed_tick` reads only `ParsedTick` fields that D3's 80 B layout carries (id, segment code, LTP, LTQ, LTT, received_at, ATP, volume, buy/sell quantities, day OHLC, OI, OI high/low). `payload_hash` is always `None`, and no greek is read. D3's field image is therefore complete as of today.
- `from_parsed_tick` has side effects on the drain: a `security_id` width refusal with a counter and `error!`, an LTP non-finite refusal, and `opt_price` NaN counting. So D3 must split out a `validate` step to keep those effects where they are, as it says.
- `AuxPacketRow::from_tick` / `from_header` also count and log a refusal (feed_aux_persistence.rs:244).
- `MAX_PRODUCER_BUFFER_BYTES` = 32 MiB, `PARKED_RESCUE_MAX_BYTES` = 4× that, and `TICK_ROW_BUFFER_PRESIZE_BYTES` = 2 MiB. All are TEXT bounds, so every design has to restate them.
- `FlushBatch::ilp_bytes()` (line 4469) and `buffer_utf8()` (2852) exist and need encode-on-demand replacements.
- `wal_defer_check` is a `fn(u64,u64,bool)->bool` (line 2361). The deferral arm needs no encoding.

Where each loses points:

- D1 snapshots labels at hand-off, which breaks the "byte-identical to today" requirement whenever a label publish lands inside a batch. The batch can be up to about 3 spans old when the queue retains, and the 09:00-09:15 attach republishes. D1 admits this.
- D3 has two weaknesses. (1) Its epoch-after-store race lets rows written between the ArcSwap store and the epoch bump keep the old table where today's code reads the new one, so identity is not exact. (2) It moves ParsedTick-to-TickRow conversion and the non-finite tripwire to the writer, which needs `validate_parsed_tick` / `from_validated`, a separate aux vector with marker records, and a greek-blindness test. That is more surface for about 20-40 ns of gain.
- D2 keeps today's per-row ArcSwap load and adds a pointer compare, so it saves nothing on label lookup. Its `stage_validate` equivalence proof is the hardest test in the set.

**Synthesis:**

FINAL PF-4 DESIGN (the synthesis). Nothing below was built or measured. Every ns figure is Assumed.

1. RECORD. The new module `crates/storage/src/tick_stage.rs` defines `#[derive(Clone, Copy)] enum StagedRow { Tick{row: TickRow, pin: u8}, Quote{row: TickRow /*ts=arrival*/, exchange_ts: Option<i64>, pin: u8}, Aux{row: AuxPacketRow, pin: u8} }`.
   - Size is pinned by `const _: () = assert!(size_of::<StagedRow>() <= 320)`.
   - The record reuses the structs the drain already builds, so `from_parsed_tick`, `opt_price`, the band, window and route gates, all refusal counters and logs, the non-finite tripwire, `note_pending_seq`, the K4 ledger note, `tick_ts_placement` and `tick_quotes::note_row` stay on the drain exactly where they are today.
   - D3's 80 B wire image is deferred to an optional PF-4c. It is taken only if the `tick_stage_push` bench shows the ~290 B copy matters. Its `TickRow::validate`/`from_validated` split is the documented route.
   - Plan corrections, carried from all three designs: the record is not ~200 B; the buffer is per batch (it is recycled through the spare lane), not per flush; nothing is serialised (spill files stay ILP text); and the rescue thread and the cold drain fallbacks encode too.

2. LABEL PINNING. This is D2's mechanism, the only one that is exact. `StagedBatch { rows: Vec<StagedRow>, pins: [Option<Arc<CandleContractLabels>>; 8], pin_count: u8 }`.
   - Per row: one `candle_contract_labels()` guard load (the same load today's encoder does, so no regression) plus an `Arc::as_ptr` compare against the last pin.
   - On a change, a #[cold] `load_full()` into the next slot.
   - A 9th distinct table inside one batch triggers `discard_pending()` (the existing durable, counted rescue tier), which is counted on `tv_tick_stage_pin_cut_total`. It is never a drop.
   - Pins are released when the writer thread clears the batch, never on the drain.
   - `write_tick_line_columns` and `append_aux_row` each gain a `labels: &CandleContractLabels` parameter; the bodies and column order are unchanged. The existing wrappers pass `&*candle_contract_labels()`.

3. DRAIN. `TickWriter.buffer: TickRowBuffer` becomes `staged: StagedBatch`. `append_row`, `append_quote_row` and `append_aux` become `stage_row(..)`.
   - Graft from D3: the buffer is reserved and pre-touched at `split_for_offload` and for each spare (one write per page, the `prefault_ring` pattern), so a DRAM-cold first fill takes no page faults inside frames.
   - Graft from D3: `rows.len() == rows.capacity()` takes a #[cold], counted path that runs `discard_pending()` (the width-cap rescue) before the push. The drain therefore never reallocates and never drops.
   - The `held >= MAX_PRODUCER_BUFFER_BYTES` cut becomes `rows >= MAX_PRODUCER_ROWS`, where `MAX_PRODUCER_ROWS = MAX_PRODUCER_BUFFER_BYTES / MAX_ILP_LINE_BYTES`.
   - `park_rescue_fits` and the spare cap move to row and record-RAM bounds. The existing const-assert keeps `MAX_PRODUCER_ROWS * MAX_ILP_LINE_BYTES * 2 <= QUESTDB_MAX_BUF_SIZE_BYTES`.
   - `offload_flush`, `install_spare_buffer`, `discard_pending`, the H4 park, the J1 `wal_defer_check` arm, the Z7 floors and `close_rescue_offload` keep their exact shapes, carrying a `StagedBatch` instead of a `TickRowBuffer`. The deferral arm encodes nothing.

4. ENCODE. One shared function, `encode_staged(rows, pins, feed, out: &mut TickRowBuffer) -> EncodeReport`, walks the rows in order through `append_within_marker` and dispatches on the existing `TickRowBuffer::{Library, Own}` match. It is called from three places:
   - (A) `TickWriterSink::write_inner`, into a scratch buffer built once at the split with the producer's encoder kind. Then the unchanged flush, retry, `note_ticks_acked(max_seq)` and rescue sequence runs.
   - (B) `TickRescueSink::rescue`, into its own scratch buffer, before `perform_tick_rescue`, with the floor released afterwards.
   - (C) The drain's cold paths: inline `spill_on_drain`, `spill_parked_*`, shutdown, and the unsplit synchronous flush. These encode inside the existing `off_worker` closure.

   Encode failure is a writer-side backstop, believed unreachable. On failure, before that batch's ack or floor release, the encoder thread calls `note_unapplied(seq)`, increments `append_dropped`, calls `ledger().note_rows_not_landed(1)`, logs `HotPath02` at powers of two with source `stage_encode_failed`, and decrements `rows`.

   Graft from D1: a writer-side text ceiling. If the encoded scratch is at or above `MAX_PRODUCER_BUFFER_BYTES`, the batch is spilled instead of POSTed, counted on `tv_tick_encoded_over_ceiling_total`. This keeps the 100 MiB questdb wedge margin even though label length is unbounded today.

   D2's full `stage_validate` is reduced to the checks proven reachable (see open questions). `IngestOutcome::WriteFailed` then covers only `TickRowError`, and encode failures are reported on the alarmed counter from the writer.

5. ZERO-LOSS ACCOUNTING.
   - The ledger identity accepted = landed + not_landed holds, because `note_row_appended` stays at the drain's acceptance point and every not-landed path, including the new encode backstop, calls `note_rows_not_landed`.
   - The watermark call order (handed_off, then acked(max) after a clean flush, then completed, plus the floors) is unchanged, because the single FIFO writer thread guarantees each backstop `note_unapplied` lands before its batch's ack.
   - Spill files are byte-identical, so `tick_spill_replay` and the curl recovery text are untouched.
   - A crash loses the staged RAM exactly as it loses ILP RAM today; the WAL recovers it.

6. AUX AND QUOTES. These are staged in the same `Vec` and order as ticks, so interleaving and batch text are preserved. Header-derived aux rows (built on the drain by `aux_row_for_non_tick`, which keeps its refusal) are staged as `Aux`. Depth level and book rows are OUT of scope. Plan PF-4b applies the same pattern to `DepthWriter` in its own PR. PF-4 alone does not get the drain under 1 µs.

7. PROOF.
   - Commit 1 (graft from D1), with no behaviour change: generate golden fixtures with today's code from a seeded `ParsedTick` and aux generator. Cover NaN, ±Inf, -0.0, zero sentinels, LTT 0 and out-of-band, out-of-window, quotes with and without a receipt, seq 0, all aux kinds, and label publishes at random points, including more than 8 publishes within one retained batch. Use random flush points and both encoders. Record the bytes plus `(rows, min, max, unbacked)` per batch.
   - Commit 2: reproduce every fixture byte for byte.
   - A proptest (≥1,024 cases per encoder) keeps the old append path verbatim under #[cfg(test)] as the oracle. It compares bytes, pending/min/max/unbacked, quote and aux counts, ledger and placement deltas, refusal counters and per-call results.
   - An end-to-end proptest drives the real split writer with a mock HTTP server that accepts or 500s at random, a full queue, width cap, park, J1 deferral and K1 shutdown. It asserts each row appears exactly once across the accepted payloads and the spill files, and that the watermark call log matches commit 1's.
   - Port the existing j1_*, h4_*, k1_*, offload and spare-lane tests; none is deleted.
   - Graft from D3: a source-scan ratchet that `append_tick_into`, `stage_row` and `append_aux` contain no `write_tick_line*`, `append_aux_row` or `IlpLine` call.
   - DHAT: 0 blocks per tick on the drain across a mid-stream label publish (one Arc increment), and 0 blocks per batch on the writer after warm-up.
   - Benches: split into `tick_stage_push` and `tick_stage_encode`; add `feed_drain/main_feed_full_frame_1_cold25k` (from D3); keep `main_feed_full_frame_4[_own]` under the `feed_drain_main_feed_full` key. New budget keys are added only after measurement.
   - Live: one session before and after, reading `hot_path_latency_minute` (drain_main_frame, receipt_to_fold) next to `tv_tick_flush_queue_full_total`, `width_capped` and the `tick_conservation_audit` verdict.
   - Same PR: a CLAUDE.md O(1)-table row for `tick_stage`.

Expected drain saving (Assumed): about 0.3-0.7 µs per tick against the own-encoder baseline, about 1.2-1.4 µs against the library encoder. Writer CPU rises by about 1 ms per 1,000 rows.

**Must fix:**

- Byte identity under label publishes: snapshot-at-hand-off (D1) and epoch-after-store (D3) both change bytes when a `candle_contract_labels` publish lands inside a batch. Use per-row pointer-compare pinning into per-batch slots (D2), and send the slot overflow through the durable counted `discard_pending` rescue, never a drop.
- Encode-failure accounting off the drain: the backstop on the writer, rescue thread and inline paths must call `note_unapplied(seq)` BEFORE that batch's `note_ticks_acked`/floor release, call `ledger().note_rows_not_landed(1)` (the drain already counted the row as appended), and increment `append_dropped`. A test must inject a mid-batch failure and assert the ledger balance and the call order.
- Restate every TEXT bound (`MAX_PRODUCER_BUFFER_BYTES` cut, `PARKED_RESCUE_MAX_BYTES`, spare-capacity cap, K6 presize) as a row or record-RAM bound with a const-assert, AND add the writer-side encoded-size ceiling (spill, never POST, at or above 32 MiB). Contract-label length is not bounded today, so a row cap alone cannot keep the 100 MiB questdb wedge margin.
- The drain must never reallocate the staged Vec: pre-touch it at split and for each spare, and route a #[cold] full-capacity hit to `discard_pending` before the push, counted.
- Golden fixtures must be generated from the unchanged code in a separate, earlier commit, and the proptest oracle must be today's append path kept verbatim under #[cfg(test)]. A re-implemented oracle makes the proof circular.
- Every rescue/spill/park/deferral/shutdown arm must be ported with its existing test: J1 `wal_defer_check` (no encode), the H4 park with the floor held, K1 `close_rescue_offload`, `rescue_abandoned` counting, and `shutdown_residue` `rows()`/`has_unbacked_rows()`. None may be weakened or deleted.
- Replace `FlushBatch::ilp_bytes()` and `TickWriter::buffer_utf8()` with test-only encode helpers, and port the M5 live-vs-replay identity test and the `drain_thread_tests`/`tick_quotes_route_tests` byte assertions to them.
- Add the source-scan ratchet so the drain append path can never call an ILP writer again, plus the CLAUDE.md O(1)-table row in the same PR.
- Correct the plan line for PF-4: the record is ~290 B (not ~200), the buffer is per batch and recycled (not per flush), the rescue thread and the cold drain fallbacks also encode, and depth book/level rows need PF-4b. PF-4 alone cannot get the drain under 1 µs.

**Open questions:**

- Can either encoder (questdb-rs `Buffer` or the own `OwnIlpBuffer`) actually refuse a row that has passed the band and window gates? If no reachable refusal exists, drop D2's full `stage_validate` and keep only the writer backstop. That leaves `IngestOutcome::WriteFailed` covering `TickRowError` alone; this needs owner sign-off because a frame-outcome label stops counting encode failures.
- Should a maximum contract-label length be enforced at publish (`sanitize_labels`), so that `MAX_ILP_LINE_BYTES` is a proven constant and not a measured estimate plus a writer-side ceiling guard?
- Rename or relabel the `rescue_parked_bytes` gauge: it will hold record RAM bytes, not ILP bytes. Is that change acceptable for the existing dashboards and alarms?
- Writer-thread headroom: tv-tick-writer is not core-pinned, and at the 12,500 ticks/s open burst it gains about 15-20 ms/s of encode work. Is one session of `queue_full`/`width_capped` readings enough to accept this, or must PF-2's core-placement measurement come first?
- Should PF-4c (D3's 80 B wire-image record with the `validate`/`from_validated` split) be committed now as a follow-up, or only if the `tick_stage_push` bench shows the ~290 B copy above about 40 ns at p99?
- Order of PF-4b (DepthWriter book rows): the 4.1/10.7 µs measured with book rows suggests depth encoding is a large share of the remaining drain time. Should PF-4b run before or in parallel with the other PF items?

## Judgment

**Winner:** Design 3 (performance-first: an 80-byte wire-image TickRecord on the drain, ILP encoded on tv-tick-writer) is the base. Design 2 supplies the loss-accounting rigour (label pins travel with the batch, the writer-side backstop runs before the ack, the floor is released after the backstop). Design 1 supplies the proof method (golden fixtures recorded on today's code in a separate first commit) and the writer-side guard that spills a batch whose encoded text would pass 32 MiB.

**Scores:**

Scored 0–10 on four criteria: correctness (zero loss, byte-identical rows), hot-path cost, diff size, testability. Total out of 40.

**Design 1, minimal-change (312 B enum of the existing row structs). Total 26/40.**
- Correctness 5. Taking the label snapshot at hand-off breaks the hard rule that every row's ILP bytes stay identical whenever a label publish lands mid-batch. The 09:00–09:15 attach republishes make that a real case, and the design admits identity holds "only for a fixed table". The loss and watermark handling is otherwise sound.
- Hot path 6. `from_parsed_tick` stays on the drain: six `tick_price_f64` calls, building 13 Options, and the 264 B row build, plus a 312 B copy. Only the text and the label probe leave the drain.
- Diff 8. About 450–650 production lines.
- Testability 7. The golden fixtures and the watermark call-log equivalence are the best proof plan of the three.

**Design 2, risk-first (about 290 B StagedRow plus up to 8 label pins per batch). Total 27/40.**
- Correctness 9. The per-batch pins keep append-time labels exact. The backstop does `note_unapplied`, then the dropped counter, then `note_rows_not_landed`, all before `note_ticks_acked`. The floor is released only after the encode and sync. The `Arc` pins are released on the writer thread. One weakness: on a 9th pin it cuts the batch through `discard_pending`, which is the counted rescue spill and not a normal hand-off.
- Hot path 5. Conversion stays on the drain, as in design 1. It adds a per-row ArcSwap guard load and pointer compare, and a runtime `stage_validate` that duplicates gates already on the drain (the in-band check already rules out a negative `ts`).
- Diff 6. About 700–900 production lines.
- Testability 7.

**Design 3, performance-first (80 B Copy image of the persisted `ParsedTick` subset). Total 30/40.**
- Correctness 7. Verified in source: `from_parsed_tick` reads only the fields the record keeps, `payload_hash` is always `None` in production, and `AuxPacketRow::from_tick` reads the same fields. So rebuilding on the writer is exact. Gaps:
  - Past 4 label switches it "keeps the latest", which is not exact.
  - A full buffer triggers `discard_pending` (a spill), where today the buffer just grows.
  - `MAX_ILP_BYTES_PER_RECORD` = 1024 depends on a contract-label length cap that does not exist (Unknown).
  - The drain-side validate split must not count non-finite optional prices a second time on the writer.
- Hot path 9. The conversion, the label probe and the text all leave the drain. What remains is one 80 B store into a pre-faulted buffer plus the existing gates and notes. The projection is about 25–45 ns; Assumed, not measured.
- Diff 6. About 550 production and 850 test lines.
- Testability 8. A cfg(test) legacy oracle, a source-scan ratchet, a DHAT test, a cold-25k bench, and the encode cost measured separately so it is not hidden.

None of the nanosecond figures has been measured. The plan's own ~1.5 µs-per-Full-tick encode figure is higher than the `tick_row_append` bench range (0.57–1.36 µs) that design 3 cites.

**Synthesis:**

**FINAL PF-4 DESIGN. Synthesis; verified against the source where stated.**

### 1. Record: design 3's 80 B image
- New module `crates/storage/src/tick_record.rs`: `#[repr(C, align(16))] #[derive(Clone, Copy)] TickRecord` with exactly the fields design 3 lists.
  - Kept raw: `capture_seq`, `received_at_nanos` (UTC), `security_id` u64, the 6 f32 prices, the u32 quantities and OI, the LTT as u32, LTQ as u16, the segment code as u8, and a tag.
  - Const-assert `size_of == 80`.
- Tags:
  - `Tick`
  - `Quote`
  - `AuxFromTick(OutOfWindowTick | ConnectSnapshot)`
  - `AuxSide(index)`, pointing into a pre-sized `Vec<AuxPacketRow>` for header-derived aux (OI, PrevClose, MarketStatus, Disconnect). This keeps tick/aux interleaving, and so batch row order, exactly as today.
- Verified in source: `TickRow::from_parsed_tick` reads only these fields and sets `payload_hash: None`; `AuxPacketRow::from_tick` reads only these fields.

### 2. Drain (`TickWriter::append_tick_into` keeps its signature)
1. **Split `from_parsed_tick`** into:
   - `validate_parsed_tick`: the side effects in today's order. First the security_id width refusal, then the non-finite LTP refusal, then `note_non_finite_optional_price` for each non-finite day OHLC / ATP.
   - `from_validated`: pure. It counts nothing and maps a non-finite value to `None`.
   - `from_parsed_tick` = validate + from_validated, so every other caller is unchanged.
2. **Compute `received_at_ist` and `ts`** with the unchanged `row_timestamp_ist_nanos`.
3. **Run the band check, `session_window::verdict` and `persist_refused_tick`** unchanged. A refused tick is pushed as an `AuxFromTick` record.
4. **Push the record.**
5. **Then, in today's order:** `pending`, `last_capture_seq`, `note_pending_seq`, `quote_rows_appended` / `tick_quotes::note_row`, the K4 `ledger().note_row_appended` (`arrival` for a quote, `ts` for a tick; Dhan only), and `tick_ts_placement::note_row`.

### 3. Labels: design 3's epoch with design 2's pin semantics
- Add `LABEL_EPOCH: AtomicU64`. It is bumped (Release) after the store in **both** publish sites; verified there are two, `publish_candle_contract_labels` (`store`) and `publish_candle_contract_labels_if_empty` (`rcu`).
- Per row the drain does one Acquire load. On a change it does `load_full()` (one Arc increment, no allocation) into the batch's switch list, `[(start_index, Arc); 8]`, and the record carries no label.
- A 9th switch inside one batch forces an early hand-off through the normal `offload_flush`. Only if that comes back retained does it go to `discard_pending`, the counted rescue. Counted on `tv_tick_label_switch_cut_total`. Never "keep the latest".
- Pinned `Arc`s are dropped on the writer or rescue thread when the batch is recycled.

### 4. Buffer: `RecordBuffer { records, aux, label_switches }`
- Reserved at `TICK_RECORD_PRESIZE_ROWS` (16,384, about 1.3 MiB) and pre-faulted once at `split_for_offload` and at each fresh reserve on the flush arm.
- Past the presize it may grow as today's text buffer grows past 2 MiB: cold, and counted on `tv_tick_record_buffer_grow_total`. It does **not** spill on full.
- The width cut in `offload_flush` becomes `retained_spans > MAX_RETAINED_FLUSH_SPANS || records.len() >= MAX_PRODUCER_RECORDS`.
- Spare lane, `FlushBatch` / `RescueBatch` / park, and every Sent / QueueFull / WidthCapped / SinkGone arm: payload type changes only.

### 5. Encode: one shared function in three places
`encode_records_into(buf: &mut TickRowBuffer, feed, rb) -> EncodeReport` walks the records in order.
- **What it calls:**
  - `Tick` / `Quote`: `from_validated`, then `count_nonfinite_tick_floats` → `TICK_NONFINITE_COLUMNS_COUNTER`, then `append_within_marker` → `write_tick_line_into` with an explicit `&CandleContractLabels` argument, then today's quote rewrite (`ts = arrival`, `exchange_ts` from the LTT).
  - `AuxFromTick`: `AuxPacketRow::from_tick`.
  - `AuxSide`: `append_aux_row`.
  - `write_tick_line_columns` and `append_aux_row` gain a `labels` parameter; existing callers pass `&*candle_contract_labels()`. The column layout and order are otherwise untouched.
- **Where it runs:**
  - (a) `TickWriterSink::write_inner`, into a scratch buffer built once at the split with the sender's encoder kind (replaces the `TickRowBufferKind` spare check).
  - (b) `TickRescueSink::rescue`, into its own scratch.
  - (c) The drain's cold paths (inline `spill_on_drain`, `spill_parked_*`, `close_rescue_offload`, the unsplit synchronous flush), into a lazily reserved scratch **inside** the existing `off_worker` closures.
  - The WAL-deferral arm encodes nothing.

### 6. Writer backstop (design 2's ordering)
- **Per failed row:** `note_unapplied(seq)`, then `append_dropped` +1, then `ledger().note_rows_not_landed(1)`, then the power-of-two `HotPath02` error with `source="ilp_append_failed"`. All of it before `note_ticks_acked(max_seq)` on the writer, and before `release_rescue_floor` on the rescue thread.
- **Over-ceiling guard (design 1):** if the encoded scratch reaches `MAX_PRODUCER_BUFFER_BYTES`, rescue/spill the batch instead of POSTing it, counted on `tv_tick_encoded_over_ceiling_total`. This keeps the questdb 100 MiB wedge margin whatever the label lengths.

### 7. Unchanged
- Rescue, spill, watermark, H4 park, J1 deferral, K1 shutdown and the Z7 floors keep their call order. Spill files are the same ILP text, so `tick_spill_replay` is untouched.
- The park bound stays at 8 batches. The byte bound is computed over record and aux RAM.

### 8. Proof (all must pass)
- **Commit 1, no behaviour change:** golden fixtures for both encoders, recorded on today's code with random flush points and label publishes. They hold batch ILP bytes plus `(rows, min, max, unbacked)`.
- **Commit 2:** reproduce the fixtures byte for byte, plus a 1,024-case proptest per encoder against the legacy append path kept verbatim under `cfg(test)`. Inputs:
  - NaN, ±Inf, ±0, subnormal values
  - LTT 0, the 1980 sentinel, out of band, and both sides of the window edges
  - receipt 0, quote route on and off, seq 0
  - every aux kind
  - more than 8 label publishes inside one retained batch
- **Assertions:** the counter deltas match (debugging recorder); the ledger and placement deltas match; the watermark call log matches; `from_validated(x) == from_parsed_tick(x)` with the optional-price counter incremented exactly once.
- **Rescue/spill file-bytes equality** on every arm.
- **DHAT:** 0 blocks per tick on the drain, including a mid-stream publish; 0 blocks per batch on the writer after warm-up.
- **Source-scan ratchet:** no `write_tick_line*`, `append_aux_row` or `IlpLine` inside `append_tick_into`, `append_row` or `append_aux`.
- **Benches:** `tick_row_append` split into `tick_record_append` and `tick_record_encode`; `feed_drain` gets a `main_feed_full_frame_1_cold25k` case.
- **One live session:** `hot_path_latency_minute` for `drain_main_frame` and `receipt_to_fold`, plus `tv_tick_flush_queue_full_total` / `width_capped`, plus the matched `tick_conservation_audit`.
- **Same PR:** a CLAUDE.md O(1) table row for `RecordBuffer` and the writer-side encode.

### 9. Out of scope
Depth level and book rows (`DepthWriter`) become PF-4b with the same shape, after PF-4 is measured. PF-4 alone does not bring the drain under 1 µs; the projection is about 2.0–2.4 µs p50 (Assumed).

**Must fix:**

- Label identity: Design 1's snapshot at hand-off and Design 3's 'keep the latest after 4 switches' both break the byte-identity rule. Pin every label table seen at append time, with switch indexes, in the batch. A 9th switch forces an early hand-off. Drop the pins on the writer or rescue thread.
- LABEL_EPOCH must be bumped in BOTH publish paths: candle_contract_labels.rs has `publish_candle_contract_labels` (ArcSwap::store) and `publish_candle_contract_labels_if_empty` (ArcSwap::rcu). The bump must come after the store or rcu. Document the race: a row appended between the store and the bump keeps the old snapshot. The contract column is not in any DEDUP key, so that row's text differs only in the label (no other column changes).
- Split from_parsed_tick so the side effects run exactly once: width refusal, then LTP refusal, then note_non_finite_optional_price, all on the drain in today's order. The writer calls a pure from_validated that does not count again. Add a proptest that from_validated equals from_parsed_tick, and that the optional-price counter fires exactly once per row.
- Do not spill on a full record buffer. Today the text buffer grows past its presize, so the record buffer must grow too (cold, counted). The width cut stays on the flush arm, using records.len() >= MAX_PRODUCER_RECORDS together with the existing retained-span cap.
- Writer-side over-ceiling guard: if the encoded scratch reaches MAX_PRODUCER_BUFFER_BYTES, spill instead of POSTing. Contract-label length is not bounded today, so a record-count cap cannot by itself guarantee the 100 MiB QuestDB wedge margin.
- Writer and rescue encode-failure backstop: note_unapplied(seq), append_dropped +1 and note_rows_not_landed(1) must all land BEFORE note_ticks_acked(max_seq) or release_rescue_floor for that batch. Test this with an injected failing row.
- Encoder parity: every scratch (writer, rescue, inline, synchronous) is built with the sender's TickIlpEncoder kind. This replaces the removed TickRowBufferKind check on the spare lane. Add a test.
- Golden fixtures must be generated by a separate first commit on today's unchanged code. Otherwise the byte-identity proof is circular. Keep the legacy append path verbatim under cfg(test) as the proptest oracle until it has been green on main for a release.
- Port the tests that read ILP off a batch (FlushBatch::ilp_bytes, TickWriter::buffer_utf8, the M5 live-vs-replay identity test, drain_thread_tests). Also port the hostile-segment tests that drive TickWriter::append_row(&TickRow) with arbitrary segment strings. A u8 segment code cannot carry those strings, so they must move to the encoder level, or a test-only TickRow path must be kept.
- Record bytes now feed the park and rescue byte gauges (rescue_parked_bytes, PARKED_RESCUE_MAX_BYTES), so the same RAM now holds more rows. Either keep a row bound that matches today's effective rows, or rename or redocument the gauge. Do not silently change what an existing gauge means.
- Add the CLAUDE.md O(1)-table row (RecordBuffer, label-switch list, writer-side encode) and the plan-file corrections in the same PR. The corrections: 80 B record, not ~200 B; a rotating spare pool, not a per-flush buffer; tick_quotes and feed_aux rows included; three encode sites, not one; and PF-4b for depth book rows.

**Open questions:**

- Should a hard maximum on contract-label length be enforced at publish, so MAX_ILP_BYTES_PER_RECORD can be derived instead of guessed? If yes, what happens to a label over the limit: refused (contract NULL) or kept, with the over-ceiling spill guard as the only backstop?
- An ILP encode failure would no longer reach the drain as IngestOutcome::WriteFailed. tv_ticks_dropped_total and note_unapplied still fire, from the writer. Does the owner accept losing that per-frame outcome label?
- Conservation ledger: a row whose encode fails on the writer is counted as accepted, then as not-landed. Today it was never counted as accepted. Does tick_conservation.rs treat not_landed as an exact term or as a tolerance? It must be re-read before merging.
- Park bound: should the H4 park stay bounded in record-RAM bytes (more rows held in RAM, so more at risk on a crash for unbacked rows), or move to a row bound equal to today's effective count?
- Writer CPU: tv-tick-writer is not core-pinned. Encoding adds about 1 ms per 1,000 rows (Assumed). Does PF-2's core placement need to cover this thread before PF-4 goes live, and which threshold on tv_tick_flush_queue_full_total / width_capped rolls PF-4 back?
- PF-4b (depth book rows through DepthWriter): ship it as a separate PR after PF-4 is measured, as all three designs recommend, or in the same release window? The sub-1 µs target needs it.
- Is the record capacity of 16,384 presized rows plus a MAX_PRODUCER_RECORDS width cut the right pair? Check against the measured open-burst rows per 500 ms span with both size triggers in LiveIngest.

## Design: PF-4 risk-first: stage typed rows on the drain, encode ILP on the writer and rescue threads, change no loss accounting

The drain keeps every gate and every counter it has today. It still builds `TickRow` / `AuxPacketRow` through `TickRow::from_parsed_tick` and `AuxPacketRow::from_tick`. It still applies the band, window and quotes-route gates in `TickWriter::append_tick_into`. It still writes the K4 ledger note, the `tick_ts_placement` note, the `tick_quotes` note, the nonfinite tripwire, and the seq-range and unbacked bookkeeping in `note_pending_seq`. The one change is the final step. Today the drain writes ILP text into a `TickRowBuffer` (through `write_tick_line_columns` or `append_aux_row` inside `append_within_marker`). Instead it pushes one `Copy` value, `StagedRow`, into a `Vec<StagedRow>` reserved in advance.

`FlushBatch` and `RescueBatch` carry that `StagedBatch` where they now carry a `TickRowBuffer`. ILP text is produced only at the three places that need bytes:
- `TickWriterSink::write_inner` on tv-tick-writer, before `sender.flush`;
- `TickRescueSink::rescue` on tv-tick-rescue, before `perform_tick_rescue`;
- the drain's existing cold fallbacks: the inline `spill_on_drain` and the unsplit synchronous `flush` arm, which already block through `off_worker`.

All three call the same functions, `write_tick_line_columns`, the `write_tick_line_into` path for `tick_quotes`, and `append_aux_row`, in the same row order, with the same `feed`, inside the same per-row marker. The spill-file format, the operator curl recovery, spill replay, the WAL capture-at-receipt, the rescue tiers, the Z7 rescue floors, the H4 park and the J1 deferral check therefore keep their meaning. They all key on rows, `min_seq`/`max_seq`/`unbacked` and floors, which are still computed on the drain from the same appends.

Two places need new mechanism; everything else just moves:
1. Contract labels. The write functions read the global `candle_contract_labels()` ArcSwap when they run. Encoding later on another thread could pick up a newer label table, so each batch pins the label tables it used.
2. Append-time encoder refusals. The per-row loss arm (`note_unapplied`, `tv_ticks_dropped_total`, `IngestOutcome::WriteFailed`) has to stay on the drain. It is replaced by a validator at stage time, proven equivalent to the encoders, plus a counted backstop on the encoding thread that should never fire.

Expected drain saving (Assumed, measure against the PF-1 own-encoder baseline): about 0.3 to 1.5 µs per tick, which is the line encoding plus the per-row label probe. The added staging cost is about 20 to 60 ns: one record copy of about 290 B, one ArcSwap load and a pointer compare.

Mistakes in the plan line:
(1) "~200 B": the record is about 290 B as an enum of the existing row structs (Assumed; pin it with a size const-assert), or 168 B packed. It is never 200.
(2) "per-flush buffer": a batch can be held across up to `MAX_RETAINED_FLUSH_SPANS`+1 spans and is recycled through the spare lane. It is a per-batch buffer, not a per-flush one.
(3) "the same write functions": the functions stay, but they read the global label table at the moment they run. They need a `&CandleContractLabels` parameter plus per-batch pins to stay byte-identical.
(4) Encoding does not leave the drain completely. The inline spill fallback and the unsplit synchronous flush still encode there. Both are cold, and both already block.
(5) The byte bounds `MAX_PRODUCER_BUFFER_BYTES`, `PARKED_RESCUE_MAX_BYTES` and the spare-capacity cap measure ILP text. Each must be restated as a row cap derived from the worst-case line length, or the 100 MiB questdb wedge margin is lost.
(6) Depth level and book rows are still encoded on the drain by `DepthWriter`. That is the "with book rows" figure, so PF-4 alone cannot bring the drain under 1 µs; it needs a depth twin (PF-4b).
(7) Tests that read ILP bytes off a batch (`FlushBatch::ilp_bytes`, the M5 live-versus-replay identity test, `TickWriter::buffer_utf8`) need an encode helper.

### Record layout

Version 1, recommended because it is identical by construction: stage the exact values the encoders already consume, with no hand-written pack/unpack. New module `crates/storage/src/tick_stage.rs`:

```
#[derive(Clone, Copy)]
pub(crate) enum StagedRow {
    Tick  { row: TickRow, pin: u8 },                                  // -> ticks (write_tick_line_into(TICKS_TABLE, .., None))
    Quote { row: TickRow /* ts_ist_nanos already = arrival */, exchange_ts: Option<i64>, pin: u8 }, // -> tick_quotes
    Aux   { row: AuxPacketRow, pin: u8 },                             // -> feed_aux_packets (append_aux_row)
}
```

For `Quote`, the drain does the same thing `append_quote_row` does today: it copies the row with `ts_ist_nanos: arrival` and computes `exchange_ts` from the LTT (`ltt != 0`). The encode step is then a plain call.

Estimated size (Assumed, not measured): `TickRow` is 264 B (5 × `Option<f64>` and 8 × `Option<i64>` at 16 B each, the `&'static str` segment at 16 B, and 5 plain 8 B fields). `AuxPacketRow` is about 272 B. So `StagedRow` is about 280 to 300 B. Pin it with `const _: () = assert!(size_of::<StagedRow>() <= 320)`. `TickRow.segment` and `AuxPacketRow.segment` stay `&'static str`. That is `Copy` and `Send`, and it keeps the hostile-segment tests valid, which a code byte could not represent.

Version 2, optional (PF-4c), only if a bench shows the about-290 B copy matters. A packed `#[repr(C)] struct PackedRow { hdr: u64, w: [u64; 20] }` of 168 B:
- `hdr`: kind u8 (0 tick, 1 quote, 2 aux), exchange segment code u8, aux kind u8, label pin u8, presence bitmask u32.
- `w[0..3]`: security_id, capture_seq, ts_ist_nanos as i64.
- Tick and quote: ltp, volume, open, high, low, close, oi, oi_day_high, oi_day_low, avg_price, last_trade_qty, total_buy_qty, total_sell_qty, received_at, payload_hash, exchange_ts. f64 is stored as `to_bits`; a value absent per the presence bit is 0.
- Aux: received_at, oi, prev_close, prev_oi, ltp, exchange_ts, volume, day_open, day_high, day_low, day_close, oi_day_high, oi_day_low, reason_code.

This needs a round-trip proptest `unpack(pack(r)) == r` that includes NaN and -0.0 bits and every segment code. It cannot carry a non-wire segment string.

Batch container, also in `tick_stage.rs`:

```
pub struct StagedBatch {
    rows: Vec<StagedRow>,                          // reserve_exact(STAGED_ROWS_PRESIZE) once
    pins: [Option<Arc<CandleContractLabels>>; LABEL_PINS], // LABEL_PINS = 8
    pin_count: u8,
}
```

- `STAGED_ROWS_PRESIZE` = 15,000. That matches K6's "about 15,000 rows per batch with no realloc" for the 2 MiB text presize, which is about 4.4 MiB staged. SPACE: at most 9 batches (producer, queue of 4, spares) × about 4.4 MiB, about 40 MiB worst case against the 13 GiB budget (Assumed).
- The `ilp_bytes()` and `buffer_utf8()` test helpers become `encode_for_test(kind) -> Vec<u8>`.

### Drain side

Who calls in: `LiveIngest::ingest_tick_at` calls `TickWriter::append_tick_with_seq` or `append_tick_quote_with_seq`, and the aux path calls `append_aux`. `TickWriter` changes as follows:

1. Field `buffer: TickRowBuffer` becomes `staged: StagedBatch`. `kind: TickIlpEncoder` is remembered so every encoder (writer, rescue, inline) builds the same buffer kind. `TickRowBufferKind` stays the sender-protocol check on the sink.

2. `append_tick_into` is unchanged up to the table choice. Then:
   - `append_row` becomes `stage_row(StagedRow::Tick{..})`;
   - `append_quote_row` becomes `stage_row(StagedRow::Quote{..})`;
   - `append_aux` becomes `stage_row(StagedRow::Aux{..})`.

   `stage_row` does the following, all O(1):
   - (a) Runs `count_nonfinite_tick_floats`, the tripwire counter, on the drain exactly as today.
   - (b) Runs `stage_validate(&row)`. This is the stage-time copy of every refusal the encoders can make on these inputs. The ones reachable from these inputs: own encoder `at_nanos` refuses a negative designated ts, and the library refuses the same (Assumed; the test settles it). The structural states (table/symbol/column order) cannot fail, because the layout is fixed code. A failure takes exactly today's append-failure arm in `append_tick_into` / `append_aux`: `note_unapplied(seq)`, `append_dropped` +1, the power-of-two `HotPath02` line, then `Err` so the drain returns `IngestOutcome::WriteFailed`. The aux arm keeps its own failure handling as today.
   - (c) Pins the label table. One `candle_contract_labels()` load (an ArcSwap guard, no refcount in the common case) and an `Arc::as_ptr` compare against `pins[pin_count-1]`. On a change it calls `load_full()` (one atomic increment per label publish per batch, never per tick) into the next slot. The row stores that slot index as `pin`.
   - (d) Pushes onto `rows` within the reserved capacity. This is a sequential write to the tail cache line, with no allocation up to the presize.
   - (e) Keeps `pending += 1`, `last_capture_seq`, `note_pending_seq`, and the `quote_rows_appended` / `aux_rows_appended` / aux counters exactly where they are today. The K4 `ledger().note_row_appended(ts)` (Dhan only) and `tick_ts_placement::note_row` run only after `stage_row` returns `Ok`, the same "accepted" point as today.

3. The label-pin overflow: a 9th distinct label table inside one batch. That can only happen while a batch is held across a full queue, and publishes are a few per day. The drain then calls `discard_pending()`, the existing durable, counted rescue tier, and stages into a fresh batch. Counted on a new local counter `tv_tick_stage_pin_cut_total`; never a drop.

4. `offload_flush` and `install_spare_buffer` move a `StagedBatch` where they move a `TickRowBuffer` today. The spare lane returns cleared `StagedBatch` values (`rows.clear()`, `pins` dropped, so the writer thread releases the label `Arc`s, not the drain). The K6 reserve becomes `rows.reserve(STAGED_ROWS_PRESIZE - len)` on the flush arm.

5. Bounds are restated in rows:
   - `MAX_PRODUCER_ROWS = MAX_PRODUCER_BUFFER_BYTES / MAX_ILP_LINE_BYTES`. `MAX_ILP_LINE_BYTES` is a const, checked by a test that encodes a maximal row in both encoders: every optional column present, the longest label, i64::MIN values, the library f64 fallback text. The const-assert `MAX_PRODUCER_ROWS * MAX_ILP_LINE_BYTES * 2 <= QUESTDB_MAX_BUF_SIZE_BYTES` keeps the wedge margin.
   - The `held >= MAX_PRODUCER_BUFFER_BYTES` cut in `offload_flush` becomes `rows >= MAX_PRODUCER_ROWS`.
   - `park_rescue_fits` counts rows against `4 * MAX_PRODUCER_ROWS`, and `parked_rescue_bytes` becomes `parked_rescue_rows`. The gauge keeps its name and reports rows × `MAX_ILP_LINE_BYTES` as an upper bound, or is renamed after asking the owner.
   - `return_spare_buffer`'s capacity check becomes `rows.capacity() > MAX_PRODUCER_ROWS`.

What leaves the drain per tick: the ILP line write, about 300 B of digit formatting, plus the `labels.get(&(id, segment))` hash probe. What stays: row construction, gates, counters, and one record copy of about 290 B.

### Writer side

There is one shared encoder function, `pub(crate) fn encode_staged(rows: &[StagedRow], pins: &[Option<Arc<CandleContractLabels>>], feed: &'static str, out: &mut TickRowBuffer) -> EncodeReport`. It walks the rows in order. For each row it runs `append_within_marker(out, ..)` and dispatches:
- `Tick` → `write_tick_line_into(out, TICKS_TABLE, feed, &row, None)`;
- `Quote` → `write_tick_line_into(out, TICK_QUOTES_TABLE, feed, &row, exchange_ts)`;
- `Aux` → `append_aux_row(out, feed, &row)`.

All three go through the existing one-match-per-row dispatch on `TickRowBuffer::{Library, Own}`. The one signature change: `write_tick_line_columns` and `append_aux_row` take `labels: &CandleContractLabels` instead of calling `candle_contract_labels()` inside. The thin wrappers the old callers use do the load. Nothing else in the layout or column order changes. `EncodeReport { encoded: usize, failed: usize }`.

Every `failed` row was already refused at stage time by `stage_validate`, so this is a backstop that should be unreachable. If one fires anyway, the encoder thread does the following, in this order, before any ack:
- `note_unapplied(capture_seq)`;
- `append_dropped` +1;
- `ledger().note_rows_not_landed(1)`, because the drain already counted it as appended;
- one coded `HotPath02` line at powers of two with `source="stage_encode_failed"`.

The marker rewind keeps the other rows.

Encoding happens in three places:
(A) tv-tick-writer, `TickWriterSink::write_inner`. It owns `encode_buf: TickRowBuffer`, built at the split with the producer's encoder kind and reserved once at `TICK_ROW_BUFFER_PRESIZE_BYTES`. It calls `encode_staged` into it, then runs the unchanged fast-reset retry / `sender.flush(&mut encode_buf)` sequence. On success it sets `landed = report.encoded` and calls `note_ticks_acked(batch.max_seq)`. On failure it runs the unchanged `rescue(batch, why)`, which spills `encode_buf.as_bytes()` (the same text today's code spills from `batch.buffer`) with `rows = report.encoded`. Then it clears `encode_buf` and returns the `StagedBatch` through the spare lane. `note_ticks_completed` and `persist_if_due_now` are unchanged.
(B) tv-tick-rescue, `TickRescueSink::rescue`. It owns a `scratch: TickRowBuffer`, encodes, then calls `perform_tick_rescue(.., scratch.as_bytes(), .., rows = encoded, ..)`. Next `note_rescue_outcome_ticks`, and only then `release_rescue_floor`, so any backstop `note_unapplied` lands while the Z7 floor is still held.
(C) Drain cold paths: the inline `spill_on_drain` from `discard_pending` past the park bound or with the thread gone, the `spill_parked_on_drain` / `spill_parked_at_shutdown` paths, and the unsplit synchronous `flush`. They encode into a lazily reserved `TickWriter.cold_encode: TickRowBuffer` inside the existing `off_worker` closure. This is already a blocking disk or network step, so the added encode (about 0.4 to 1.5 µs × rows, up to tens of ms for a full batch) is inside a path that already waits on disk. That is flagged, not hidden.

The WAL-deferral arm of `discard_pending` (`wal_defer_check` passes) encodes nothing. It drops the staged rows, so it is cheaper than today.

Writer CPU: at the 12,500 ticks/s open burst, about 19 ms/s of extra encoding on tv-tick-writer (Assumed). PF-2's core-placement measurement should include this thread.

### Rescue, spill, watermark

Every failure path, and how a staged row survives it. Each is unchanged in fate and counters versus today.
1. Writer behind (queue full): `offload_flush` gets the `StagedBatch` back from `TrySendError::Full`. Rows, range and unbacked flag are restored exactly as today. A retained batch keeps staging, within its presize and then by `Vec` growth, as the text buffer grows today. Pins persist. The span cut (`MAX_RETAINED_FLUSH_SPANS`) or the row cut (`MAX_PRODUCER_ROWS`) calls `discard_pending`, so the outcome is `WidthCapped`, as today.
2. `discard_pending` with the rescue split in place: it holds the Z7 floor (`hold_rescue_floor(Ticks, min, max)`) BEFORE the move, then does `try_send(RescueBatch{staged,..})`. Sent: `note_ticks_handed_off`. Full: the H4 park applies when `min_seq == 0 || unbacked` and the row-based bound allows; the floor stays held and the batch is parked as staged rows, not text, so it is smaller. Otherwise the floor is released, the J1 `wal_defer_check` decides between deferring (rows dropped, counted on `tv_ticks_dropped_total` and `note_ticks_not_landed`) and the inline spill via the cold encoder. Disconnected: same as Full minus the park.
3. Rescue thread: encode, spill (synced off the drain), then `note_rescue_outcome_ticks`, then `release_rescue_floor`, then `note_ticks_completed`. The ordering keeps the persisted watermark held below the batch until its text is synced or marked. An abandoned batch at shutdown never releases its floor, as today, so the range stays replayable.
4. Writer flush failure (reset, timeout, refused): the bounded retry re-sends the same `encode_buf` bytes, which are idempotent through `capture_seq` in `DEDUP_KEY_TICKS`. On final failure `TickWriterSink::rescue` spills those bytes. The spill file is the same ILP text as today, byte for byte. So `tick_spill_replay` (line bisection, quarantine), the curl recovery text and the `spill_dir_bytes` caps all work unchanged.
5. No sender, or the synchronous arm: encode on the drain inside `off_worker`, then send or spill as today.
6. Shutdown: `close_offload_queues` calls `discard_pending` then `close_rescue_offload` (the K1 deadline hand-off of parked staged batches, the cold inline encode for a timeout or a gone thread, and `tv_ticks_lost_total{source="rescue_abandoned"}` only when the inline write also fails and the fate is lost). Batches abandoned in the writer queue are counted by `shutdown_residue::OffloadQueue` via `rows()` and `has_unbacked_rows()`, both unchanged.
7. Crash or kill: staged rows in RAM are lost exactly as ILP bytes in RAM are lost today. They come back from the WAL (capture-at-receipt, replay-stable `capture_seq`). Unbacked rows (`mark_pending_unbacked`, minted seq 0) have the same exposure window as today; no new window.
8. WAL replay (boot STAGE-C and the catch-up `replay_chunks`): it goes through the same `LiveIngest` / `TickWriter`, so its rows stage and encode identically. `replay_rows_held` (`writer.pending()`) still counts rows held by the producer, so the LH-02/M2 pacer is unchanged.

Watermark: `pending_min_seq`, `pending_max_seq`, `pending_unbacked`, `note_ticks_handed_off`, `note_ticks_acked(max_seq)` (writer thread, after the flush), `note_ticks_completed` and the rescue floors are all produced from the same events in the same order. The only new mark site is the backstop `note_unapplied` on an encode thread. It is atomic bucket marking, safe off the drain. It always runs before that same batch's ack or floor release; the single FIFO writer thread rules out a later batch acking first.

Conservation ledger (K4): `note_row_appended` stays at the drain's stage acceptance point (the Dhan writer, same `ts`). `note_rows_not_landed` keeps its existing sites (sink rescue, the deferral arm) and gains exactly one: the backstop encode failure. Today's identity, accepted = landed + not_landed, therefore still holds.

### Aux, quotes, depth

- `tick_quotes` (M5, Quotes 41/43): the route is still decided on the drain from the packet and its WAL receipt (`tick_quote_route`). The `received_at` check is kept: a packet with no receipt stays `Tick`. It is staged as `Quote` with `row.ts_ist_nanos = arrival` and `exchange_ts = (ltt != 0).then(..)`. It encodes via `write_tick_line_into(TICK_QUOTES_TABLE, ..)`. Live and replay produce the same staged value, so the M5 identity test now encodes via `encode_for_test`.
- `feed_aux_packets`: rows from `ingest_non_tick_at`, `append_aux_tick` (connect snapshot) and `persist_refused_tick` (out-of-window and out-of-band ticks) are staged as `Aux` in the SAME `Vec` as tick rows. Interleaving, and therefore the ILP line order of a mixed batch, is preserved. They share the rescue and spill tiers and the watermark range as today. `append_aux_row` keeps `sanitize_ilp_symbol` on segment, feed, kind and contract at encode time. That is deterministic, so moving it is identity-safe.
- Depth: OUT OF SCOPE of PF-4 as written, and this is the biggest plan gap. In production (array rows on), `append_inline_depth_book` writes 2 `market_depth_book` rows per Full packet through `DepthWriter` on the drain, and the dev shape writes 10 level rows. The measured "with book rows 4.1/10.7 µs" includes that encoding. Recommend PF-4b, applying the same pattern to `DepthWriter` (`split_for_offload`, `DEPTH_PARKED_RESCUE_*`, the same floor and park names), as a separate PR after PF-4 lands. Doing both at once doubles the rescue surface under review.

### Proof plan

1. Byte-identity proptest (`crates/storage/tests/tick_stage_identity_proptest.rs`, ≥1,024 cases per encoder kind). Inputs: random streams of `ParsedTick` (NaN, ±Inf, 0.0 sentinels, -0.0, i64 and u32 extremes, bit-63 security ids, in-band and out-of-band and out-of-window timestamps, receipt 0 or present, quote route on or off), plus aux packets (all 6 kinds), plus label-table publishes at random points (including more than 8 publishes inside one retained batch). Old path: today's `append_*` into a `TickRowBuffer`. New path: stage, then `encode_staged`. Asserts: the concatenated bytes are equal per batch; `pending`, `min_seq`, `max_seq`, `unbacked`, `quote_rows_appended`, `aux_rows_appended`, `IngestOutcome`/`Err` per call, ledger `note_row_appended` counts, and `append_dropped` are equal. The batch-cut points are equal except for counted pin cuts.
2. `stage_validate` soundness proptest: for every row it accepts, `encode_staged` reports `failed == 0` in BOTH encoders. For every row it refuses, today's append also returns `Err`.
3. Encode-failure backstop test, with an injected failing row through a `#[cfg(test)]` encoder hook. Checks that `note_unapplied(seq)` lands before `note_ticks_acked`, that `append_dropped` and `note_rows_not_landed` each rise by 1, and that the other rows land.
4. Rescue and spill tests, each comparing the spill-file bytes with the old path:
   - WidthCapped (queue full for 3 spans, then the rescue thread);
   - SinkGone (inline cold encode);
   - writer flush failure (`TickWriterSink::rescue`);
   - H4 park, then retry, then the K1 shutdown deadline (timeout, gone, and inline-failure → `rescue_abandoned`);
   - the J1 deferral arm (no encode, counters equal);
   - Z7: the floor is held while queued or parked and released only after the encode plus sync. The existing `j1_*` and `close_rescue_offload` tests are ported, not deleted.
5. Bounds: test that `MAX_ILP_LINE_BYTES` covers a maximal row in both encoders, and the const-assert wedge margin on `MAX_PRODUCER_ROWS`.

### Risks

1. (Risk) Label snapshot. If pins were skipped, rows encoded after a label publish would carry the new name. The design pins per batch; a 9th distinct table inside one batch forces a durable rescue cut (counted). `contract` is not in any DEDUP key, so even a residual mismatch would be cosmetic, but byte identity is required, hence the pins.
2. (Risk) Encoder refusal moving off the drain. This is closed only if `stage_validate` is exactly as strict as both encoders: proptest 2. The library's negative-timestamp behaviour is Assumed until that test runs.
3. (Risk) Drain cold paths still encode: the inline spill with a gone or full rescue thread, the synchronous arm, shutdown. Encoding a full batch there adds up to tens of ms on the drain, on a path that already does a disk write. Flagged, not hidden.
4. (Risk) Bounds are restated in rows. A wrong `MAX_ILP_LINE_BYTES` would let a batch encode past 32 MiB toward the 100 MiB questdb wedge; the const-assert test on a maximal row prevents that.
5. (Limitation) Staged RAM is about 2× the text bytes per row (about 290 B against about 140 B). Worst-case SPACE is about 40 MiB across 9 batches (Assumed).
6. (Limitation) The writer thread does more CPU work, about 19 ms/s at the open burst (Assumed). In a QuestDB stall the queue fills on network time, not encode time, so the fill rate is unchanged.
7. (Limitation) Depth level and book rows are still encoded on the drain until PF-4b. The under-1 µs goal is not reachable from PF-4 alone.
8. (Assumed) The 280 to 300 B `StagedRow` size and the ns savings are estimates from field counts and the PF measurement. None were measured; the build is not run here.
9. (Risk) Size of change: one writer type is touched across about 15 rescue and park tests. It needs the 3-agent review (hot-path, security, hostile) before and after, per charter §E.

## Design: PF-4 minimal-change: TickWriter buffers Copy row records, writer/rescue threads encode with the unchanged write functions

Design only. Nothing was edited, built or run. I read `tick_persistence.rs` (TickWriter, append_tick_into, append_row, append_quote_row, append_aux, offload_flush, install_spare_buffer, discard_pending, park/retry, TickWriterSink::write_inner/rescue, TickRescueSink::rescue, FlushBatch, RescueBatch), `tick_ilp.rs` (IlpLine, TickRowBuffer, TickIlpSender::flush), `feed_aux_persistence.rs` (AuxPacketRow, append_aux_row), `candle_contract_labels.rs`, and the app call sites (`LiveIngest` append, `flush_ticks`, the offload/rescue thread spawn, drain_thread_tests, tick_quotes_route_tests).

The change is one type. The producer field `TickWriter::buffer: TickRowBuffer`, which holds ILP text, becomes `records: TickRecordBuffer`, a pre-reserved `Vec<TickRecord>`. `TickRecord` is a 3-variant `Copy` enum holding the structs the drain already builds: `TickRow`, `TickRow` plus the quote's exchange time, and `AuxPacketRow`. Everything else on the drain stays where it is: `from_parsed_tick`, the band and session-window gates, the routing between ticks, tick_quotes and feed_aux, `note_pending_seq` with min/max/unbacked, the conservation ledger, `tick_ts_placement`, and the counters. Only the text step changes: `append_within_marker(write_tick_line_into / append_aux_row)` becomes `records.push(record)`.

The existing hand-off queue (`FlushBatch`), rescue queue (`RescueBatch`), RAM park, spare-return lane, width cap and watermark floors keep their shapes. They now carry record Vecs instead of text buffers. Text is produced in three places by the SAME unchanged functions (`write_tick_line_columns`, `append_aux_row`, under `append_within_marker`):
1. `TickWriterSink` (tv-tick-writer thread), into one reused scratch `TickRowBuffer`, just before `sender.flush`.
2. `TickRescueSink` (tv-tick-rescue thread), into its own scratch, before `perform_tick_rescue`.
3. The drain's existing cold inline-spill fallback and the unsplit synchronous `flush`, inside the same `off_worker` closure that already wraps the file write or the HTTP round trip.

Because records are encoded in insertion order, each batch's ILP bytes equal today's for the same contract-label snapshot. To keep that deterministic, the label snapshot (one `Arc` clone per batch, never per tick) is taken at hand-off and travels with the batch.

The plan line needs these corrections:
(a) The record is not ~200 B. Reusing `TickRow` gives 264 B, `AuxPacketRow` about 304 B, and the enum about 312 B (Assumed, to be pinned by a `size_of` test). A ~150 B record would need a new presence-bitmask struct, which is not a minimal change.
(b) "Binary record": nothing is serialised. The record never leaves the process; the WAL keeps raw frames and the spill keeps ILP text.
(c) "The writer thread encodes": the rescue thread, the drain's inline-spill fallback and the synchronous flush path must encode as well.
(d) "Byte-identical to today" holds only for a fixed contract-label table, because the label read moves from append time to hand-off time.
(e) Today's byte bounds measure TEXT (`MAX_PRODUCER_BUFFER_BYTES` held check, `PARKED_RESCUE_MAX_BYTES`, the spare-return cap, `TICK_ROW_BUFFER_PRESIZE_BYTES`). They become record-count/RAM bounds, plus a writer-side text-ceiling guard, because contract-label length is unbounded.
(f) The "with book rows 4.1/10.7 µs" figure comes from `DepthWriter`'s `market_depth_book` rows, a separate writer this item does not cover. It needs a PF-4b of the same shape over `DepthFlushBatch` / `DepthRescueBatch`.
(g) An ILP encode failure can no longer be returned to the drain per tick. `IngestOutcome::WriteFailed` stays reachable only for `TickRowError`; an encode loss is counted on the writer thread instead.

### Record layout

```rust
// crates/storage/src/tick_persistence.rs (new, beside TickRow)
#[derive(Clone, Copy, Debug, PartialEq)]
pub(crate) enum TickRecord {
    Tick(TickRow),                                   // -> write_tick_line_into(buf, TICKS_TABLE, feed, &row, None, labels)
    Quote { row: TickRow, exchange_ts: Option<i64> },// row.ts_ist_nanos already = arrival; -> write_tick_line_into(buf, TICK_QUOTES_TABLE, feed, &row, exchange_ts, labels)
    Aux(AuxPacketRow),                               // -> append_aux_row(buf, feed, &row, labels)
}
pub(crate) struct TickRecordBuffer { records: Vec<TickRecord> }  // push / len / clear / capacity / reserve_exact / prefault
```

Sizes on 64-bit (Assumed; pinned by `test_tick_record_size_is_pinned`, assert ≤ 320):
- `TickRow` = 264 B: `security_id` i64 8, `segment` &'static str 16, `ltp`/`volume`/`ts`/`capture_seq` 4×8 = 32, five `Option<f64>` (open, high, low, close, avg_price) 5×16 = 80, eight `Option<i64>` (oi, oi_day_high, oi_day_low, last_trade_qty, total_buy_qty, total_sell_qty, received_at, payload_hash) 8×16 = 128.
- `Quote` = 264 + 16 = 280 B.
- `AuxPacketRow` ≈ 304 B: kind, sid, segment, ts, 15 options, capture_seq.
- Enum ≈ 312 B.

No new field semantics: every value is the one the drain computes today. `TickRow` is built by `from_parsed_tick` (rounding via `tick_price_f64`, NaN→NULL with its counter, zero-sentinel→NULL, `row_timestamp_ist_nanos`). `Quote` = `TickRow { ts_ist_nanos: arrival, ..row }` as in `append_quote_row`, plus `exchange_ts = (ltt != 0).then(|| ltt as i64 * 1e9)`. `Aux` = `AuxPacketRow::from_tick` / `from_header`, unchanged.

Bounds:
- New `TICK_RECORD_PRESIZE_ROWS = 16_384` (≈5.1 MB, Assumed) replaces the producer's use of `TICK_ROW_BUFFER_PRESIZE_BYTES` (2 MiB of text ≈ 15k rows today).
- New `MAX_PRODUCER_RECORDS = 65_536` (≈20 MB RAM) replaces the `held >= MAX_PRODUCER_BUFFER_BYTES` text check on the QueueFull arm.
- The park bound stays in bytes but is computed as `records.len() * size_of::<TickRecord>()` against the unchanged `PARKED_RESCUE_MAX_BYTES`; it bounds RAM, which is what parking costs.
- Spare-return drop rule: `records.capacity() * size_of` > `MAX_PRODUCER_BUFFER_BYTES`.

Rejected alternative: a compact record with `segment` as a u8 code, `f64` plus a u16 presence mask, and an i64 for every option. That is ~150 B, but it is a new struct with a new lossless conversion and its own proptest. It is a possible later step, not part of the minimal change.

### Drain side

What stays: `TickWriter::append_tick_with_seq` / `append_tick_quote_with_seq` / `append_aux` keep their signatures, so `LiveIngest` and `append_aux_tick` in `dhan_feed_stack.rs` need no change. `append_tick_into` is unchanged up to the table choice, including `from_parsed_tick`, the `MIN/MAX_PLAUSIBLE_EXCHANGE_TS_SECS` band, `session_window::verdict`, `persist_refused_tick`, the conservation-ledger `note_row_appended` (ticks: `row.ts_ist_nanos`; quotes: `arrival`), `tick_ts_placement::note_row`, `tick_quotes_persistence::note_row` and `quote_rows_appended`.

What changes:
- `append_row(&row)`: tripwire `count_nonfinite_tick_floats` (kept on the drain, 6 compares) → `self.records.push(TickRecord::Tick(*row))` → `pending += 1`, `last_capture_seq` max, `note_pending_seq`. No marker and no rewind are needed: pushing a `Copy` struct into reserved capacity cannot half-fail.
- `append_quote_row`: push `TickRecord::Quote`.
- `append_aux`: push `TickRecord::Aux(*row)`, plus `aux_counters` and `note_pending_seq` as today. Its `Err` arm (note_unapplied + `append_dropped` + throttled error) moves to the encoder sites.

Cost per accepted row: a ~312 B memcpy into a resident buffer. O(1), zero allocation below `TICK_RECORD_PRESIZE_ROWS`. Past that, the Vec doubles, exactly as the text buffer does past 2 MiB today. The ILP text work, number formatting and the per-row `candle_contract_labels()` ArcSwap load plus hash probe all leave the drain.

Hand-off (`offload_flush`): unchanged in shape. `FlushBatch { records, labels: Arc<CandleContractLabels>, rows, min_seq, max_seq, unbacked }`. The new `labels` is one Arc clone per batch (one atomic increment), loaded at the hand-off instant. `try_send`; Sent / QueueFull / WidthCapped / SinkGone arms are identical, except the width cut reads `retained_spans > MAX_RETAINED_FLUSH_SPANS || records.len() >= MAX_PRODUCER_RECORDS`.

Spare buffers:
- `install_spare_buffer` takes a recycled record Vec from the existing spare lane (`Receiver<TickRecordBuffer>`). The `TickRowBufferKind` protocol check goes away, because records carry no protocol.
- If no spare is waiting, it reserves `TICK_RECORD_PRESIZE_ROWS` on the flush arm, as K6 does.
- At `split_for_offload` the first producer buffer and the spares are pre-touched once (one write per page, the `prefault_ring` precedent), so a DRAM-cold first fill takes no page faults inside frames. Recycled spares are already resident.

Synchronous (unsplit) `flush`: inside the existing `off_worker` closure, encode `records` into `self.sync_scratch: TickRowBuffer` (presized at construction from the configured `TickIlpEncoder`), then `sender.flush(&mut sync_scratch)`. Ack semantics are unchanged. Only tests and a failed writer-thread spawn use this path.

`TickWriter` keeps `encoder: TickIlpEncoder`, so every scratch it builds matches the sender's encoder.

### Writer side

`TickWriterSink` gains:
- `scratch: TickRowBuffer`, built with `TickRowBuffer::new(encoder)` at `split_for_offload` and reserved to `TICK_ROW_BUFFER_PRESIZE_BYTES`.
- `encoder`.
- The resolved `append_dropped` counter handle (same name `tv_ticks_dropped_total{feed}`).

`write_inner(batch)`:
1. Return 0 if `rows == 0`.
2. `encode_records(&mut self.scratch, feed, &batch.labels, &batch.records)`. This is ONE shared function that loops the records in order. Each record goes through `append_within_marker(scratch, |b| match b { Library(x) => write_tick_line_columns(x, table, feed, row, ex_ts, labels), Own(x) => … })` or `append_aux_row(x, feed, aux, labels)`. These are the same functions and the same marker/rewind as today, with the per-row global label load replaced by the batch's `labels` parameter.
3. A per-record encode `Err` (practically unreachable, Assumed: literals are prevalidated and values escaped) does today's drain-side failure handling on this thread:
   - `applied_watermark().note_unapplied(seq)`
   - `append_dropped.increment(1)`
   - `ledger().note_rows_not_landed(1)` for Dhan
   - power-of-two coded `HotPath02WriterQueueDrop` with `source="ilp_append_failed"` (the existing log key)
   - `batch.rows -= 1`
4. Text guard: if `scratch.len() >= MAX_PRODUCER_BUFFER_BYTES` (32 MiB), the batch is not POSTed. It goes to the existing `self.rescue(batch, "encoded batch over the producer ceiling")` (spill, counted). Spill files take any size. This keeps today's guarantee that a commit never comes near the 100 MiB questdb-rs wedge, whatever the label lengths. It is unreachable at realistic row text (~300 B × 65,536 ≈ 20 MB, Assumed) and counted on a new `tv_tick_encoded_over_ceiling_total`.
5. Then today's code unchanged: `sender.flush(&mut self.scratch)`, the one fast retry on the same bytes, `note_ticks_acked(batch.max_seq)` on Ok, rescue on Err.

`rescue(batch, why)` now writes `self.scratch.as_bytes()`, the already-encoded text (same `spill_failed_ilp` call, same counters and message). The scratch is then cleared and the record Vec is cleared and returned through `return_spare_buffer`.

Steady state is zero allocation: the scratch grows once to the largest batch and is kept. It is dropped and re-reserved only if its capacity exceeds `MAX_PRODUCER_BUFFER_BYTES`, mirroring the spare rule.

Cost (Assumed): own encoder ~0.4–0.8 µs per row, about 2.5–4 ms of writer CPU per second at 5,000 ticks/s, before the POST it already does. The queue depth (4) and `MAX_RETAINED_FLUSH_SPANS` (2) are unchanged, so encode time eats into the existing backpressure budget rather than adding a new one.

`TickRescueSink` gains `scratch` + `encoder`, and `rescue(&mut self, batch)` calls the same `encode_records` before `perform_tick_rescue(payload = scratch.as_bytes(), …)`. The app's rescue-thread closure binds `let mut rescue_sink`.

### Rescue, spill, watermark

These stay identical by keeping every decision on the drain and moving only the text:
- `pending_min_seq`, `pending_max_seq` and `pending_unbacked` are computed by the same `note_pending_seq` at push. `take_pending_range` / `restore_pending_range` are unchanged.
- `FlushBatch` and `RescueBatch` carry the same `min_seq`, `max_seq`, `unbacked` and `floor`.
- The applied watermark sees the same sequence of calls in the same order: `note_ticks_handed_off` on Sent and on park/rescue queue, `note_ticks_acked(max_seq)` only after QuestDB acks or a writer-thread spill lands (`in_order=true`), `note_ticks_completed` + `persist_if_due_now` in `TickWriterSink::write`, and `hold_rescue_floor` / `release_rescue_floor` in `discard_pending` and the park.

`discard_pending` keeps all four arms:
1. Rescue thread: a `RescueBatch` with records + labels Arc.
2. H4 park when `range.0 == 0 || unbacked`, bounded by `PARKED_RESCUE_MAX_BATCHES` and the RAM-byte bound.
3. J1 WAL deferral via `(self.wal_defer_check)(min, max, unbacked)`, which drops the records exactly as it drops text today.
4. Inline spill. `spill_on_drain` takes the records and encodes into `self.inline_scratch` INSIDE the existing `off_worker` closure, before `perform_tick_rescue`. This is cold, already a blocking file write. The scratch is zero-capacity until first use, and the allocation stays in this rare arm.

`spill_parked_on_drain` / `spill_parked_at_shutdown` / `close_rescue_offload` (K1 deadline, `rescue_abandoned` loss count) take the same inline-encode path.

The fate of each row (spilled / deferred / lost) and every counter (`tv_ticks_dropped_total`, `tv_ticks_spilled_total`, `tv_tick_rescue_*`, `note_ticks_not_landed`) are the same per batch. Spill files contain the same ILP text, so `tick_spill_replay` is untouched.

Two shutdown accessors keep their meaning: `RescueBatch::rows` / `has_unbacked_rows` and `FlushBatch::rows` / `has_unbacked_rows` (J2). Abandoned work stays countable in rows.

Conservation ledger: `note_row_appended` stays at the drain push site with the same ts arguments. The one semantic shift: a row whose ILP encode fails is now counted as appended at push and then as `note_rows_not_landed(1)` on the writer. Today it was never counted as appended. The daily check reads accepted rows against the database with not-landed as a tolerance, so its verdict is unchanged in the normal case. Assumed until `tick_conservation.rs`'s comparison is re-read in the implementing PR.

The size-trigger and replay pacer (`LiveIngest::pending_rows`, `replay_rows_held` via `writer.pending()`) count rows, not bytes, so they are unchanged.

### Aux, quotes, depth

`tick_quotes` and `feed_aux_packets` share the ticks writer's buffer today and keep sharing it, as two more variants of the same record enum.

Insertion order across ticks, tick_quotes and feed_aux in one batch is preserved, so the concatenated batch text equals today's. `drain_thread_tests` concatenates `ilp_bytes()`, and tick_quotes_route_tests compares live vs replay text.

`append_aux_row`'s per-symbol `sanitize_ilp_symbol` (a Cow that may allocate on a dirty value) now runs on the writer thread, which is strictly better for the drain.

`write_tick_line_columns` and `append_aux_row` each gain one parameter, `labels: &CandleContractLabels`, in place of the internal `candle_contract_labels()` global load. The body, column order and the `label_is_ilp_clean` debug check are unchanged.

`FlushBatch::ilp_bytes()` (borrowed text) cannot exist any more. It is replaced by `FlushBatch::encode_ilp(&self, encoder) -> Vec<u8>`, a diagnostic for tests that allocates and is never called on the drain. The two app test files move to it (`drain_thread_tests.rs`, `tick_quotes_route_tests.rs`).

`tick_quotes_persistence.rs`: no code change. The table constant and `note_row` are reused.

Depth is NOT covered. `market_depth` / `market_depth_book` rows come from `DepthWriter::append_*` in `depth_persistence.rs`, which has its own `DepthFlushBatch`, `DepthRescueBatch`, park and spare lane. The task's "with book rows 4.1/10.7 µs" line is that writer. It needs PF-4b with the identical shape: a book record of 2 sides × 5 levels, already fixed-size from the Full packet. I recommend a separate PR after PF-4 lands and is measured, so the two byte-identity proofs stay independent.

### Risks

These are the ways this design can go wrong. Each is flagged and none is hidden.

1. **Label timing (behaviour change):** the `contract` symbol is read at hand-off, not at append. Rows appended up to one flush span (500 ms) before the hand-off, or up to about 3 spans when the queue retains, take the newer table. During the 09:00–09:15 attach republishes, a row can gain a contract name it would have lacked today, or with `preferred_option_rows` changes take a different name. Byte identity is proven only for a fixed table. Mitigation: the snapshot per batch is deterministic; the alternative of one Arc per row is rejected because it costs an atomic per tick.

2. **Memory:** records are about 2.2× the size of the text (312 B vs ~140–300 B). Producer plus 4 queued plus 4 spares ≈ 9 × 5.1 MB ≈ 46 MB, against ≈ 18 MiB of text today. Writer and rescue scratches add about 2–32 MiB. The park bound is now RAM bytes, so at most 128 MiB of records as today. Assumed to fit the Quote 38 budget (6 GiB app+OS worst case); not measured.

3. **Writer CPU and backpressure:** encoding now precedes each POST on the writer thread. A slower writer fills the 4-deep queue sooner, retained spans hit `MAX_RETAINED_FLUSH_SPANS`, and more batches go to the rescue/spill tier under QuestDB stalls. The same bounded, counted direction as today, but reachable earlier. Measure `tv_tick_flush_queue_full_total` and `width_capped` for one session.

4. **Lost per-tick failure signal on the drain:** an ILP encode error no longer returns `Err` to `LiveIngest`, so `IngestOutcome::WriteFailed` and its frame-outcome label no longer count encode failures (`TickRowError` still does). The alarmed `tv_ticks_dropped_total` and `note_unapplied` still fire, from the writer thread. Encode errors are believed unreachable (Assumed).

5. **Ledger semantic shift:** an encode-failed row is now counted as accepted and then not-landed, where today it was never counted. The daily conservation verdict needs re-reading in the implementing PR.

6. **Text ceiling:** contract-label length is unbounded, so the record cap alone cannot guarantee text < 32 MiB. The writer-side over-ceiling spill covers it, but that path is new code on a never-expected arm and needs its own test.

7. **Inline-spill fallback encodes on the drain:** it is inside `off_worker` with the file write, but up to 65,536 rows ≈ 30–60 ms (Assumed) of extra block on an arm that already blocks.

8. **Golden fixtures must be generated on the pre-change code in a separate commit.** Generating them after the move would make the proof circular.

9. **DRAM-cold first fill:** without the one-time pre-touch, the first batch after boot faults about every 13 records. The pre-touch is O(capacity) once per buffer at split (~5 MB each).

10. **Depth book rows are not covered** (PF-4b), so the "with book rows" drain figure improves only by the tick share.

11. **Expected gain is not measured.** It is inferred from the task's ~1.5 µs ILP-encode figure; the real per-tick saving must come from the feed_drain bench and the one-session live read.

## Design: PF-4 performance-first: 80-byte wire-image TickRecord on the drain, ILP encoded on tv-tick-writer

Read-only design from the code; no edits, builds or cargo runs. Today `TickWriter::append_tick_into` does all of this on the frame drain for every accepted tick: `TickRow::from_parsed_tick` (six price conversions, Option building, optional-price NaN counting), the in-band and session-window checks, `count_nonfinite_tick_floats`, an ILP marker, `write_tick_line_columns` (an ArcSwap load plus a contract-label hash probe, then about 17 encoded columns), the pending/seq bookkeeping and the ledger and placement notes. PF-4 splits that work. The DECIDE part stays on the drain unchanged, so every refusal, route, counter and log fires at the same point as today. The CONVERT and ENCODE part moves to the existing `tv-tick-writer` thread, which already exists and already does the network flush. The drain stores an 80-byte, Copy, field-for-field image of the persisted ParsedTick subset into a pre-faulted Vec. That is one sequential 80-byte store, 4 records per 5 cache lines, no conversion, no label probe, no text. The writer rebuilds the ParsedTick subset and calls the SAME functions on the same inputs: `TickRow` conversion, `write_tick_line` / `write_tick_line_into`, `AuxPacketRow::from_tick`, `append_aux_row`, `append_within_marker`. So bytes are identical by construction, and a proptest compares the old path with the new one. Expected per-tick drain cost for the row stage: about 20-40 ns, down from about 0.8-1.5 µs (Assumed until measured). The encode cost does not disappear: about 1 ms of CPU per 1,000-row batch moves to the writer thread.

Five corrections to the plan line:
(1) "~200 B record" is the wrong size. The persisted subset fits in 80 B. Storing the converted TickRow would be 264 B (13 Options at 16 B each plus a &str) and would keep the conversion on the drain.
(2) "a pre-allocated per-flush buffer" must be a rotating pool through the existing spare lane, because FlushBatch, RescueBatch and the parked-rescue queue all have to carry records.
(3) `tick_quotes` rows and `feed_aux_packets` rows share this buffer today. They must move with the tick rows, or batch row order and the spill-file bytes change.
(4) The inline depth BOOK rows (2 per Full packet, through `append_inline_depth_book` → `DepthWriter`) are still ILP-encoded on the drain. They are probably most of the measured 4.1 µs vs 3.2 µs gap. Under 1 µs per tick is NOT reachable with PF-4 alone; a PF-4b applying the same record machinery to DepthWriter is needed.
(5) The contract label is resolved at encode time unless the snapshot is pinned per batch. The design pins it with a label epoch so the bytes are exact.

### Record layout

New module crates/storage/src/tick_record.rs.

#[repr(C, align(16))] #[derive(Clone, Copy)] pub struct TickRecord — exactly 80 B, compile-time asserted with `size_of == 80` and `align_of == 16`:
  0  capture_seq: i64 — as passed to append_tick_with_seq (seq 0 or freshly minted still sets pending_unbacked, same as today)
  8  received_at_nanos: i64 — ParsedTick::received_at_nanos, raw UTC, 0 = none; the IST conversion happens at encode, exactly as from_parsed_tick does it
 16  security_id: u64 — ParsedTick verbatim, no narrowing; the width check already ran on the drain
 24  last_traded_price: f32
 28  average_traded_price: f32
 32  day_open: f32
 36  day_close: f32
 40  day_high: f32
 44  day_low: f32
 48  volume: u32
 52  total_sell_quantity: u32
 56  total_buy_quantity: u32
 60  exchange_timestamp: u32 — LTT, IST seconds
 64  open_interest: u32
 68  oi_day_high: u32
 72  oi_day_low: u32
 76  last_trade_quantity: u16
 78  exchange_segment_code: u8
 79  tag: u8 — RecordTag: Tick=0, Quote=1, AuxFromTick{OutOfWindowTick, ConnectSnapshot}=2|3, AuxSide=4. For AuxSide, the security_id slot holds the index into the side vector.
The greeks (iv/delta/...) are not persisted by from_parsed_tick, so they are omitted. `TickRecord::to_parsed_tick()` rebuilds a ParsedTick with those fields zeroed. A unit test pins that from_parsed_tick reads none of them (a source scan plus a proptest over random greeks).

pub struct RecordBuffer { records: Vec<TickRecord>, aux: Vec<AuxPacketRow>, label_switches: [(u32, Option<Arc<CandleContractLabels>>); 4], switch_len: u8 }.
- records: capacity MAX_PRODUCER_RECORDS = MAX_PRODUCER_BUFFER_BYTES / MAX_ILP_BYTES_PER_RECORD (1024) = 32,768, which is 2.5 MiB. It is pre-faulted once at construction (`vec![TickRecord::ZERO; cap]` then `clear()`, the seal-ring prefault pattern), so the drain never pays first-touch page faults, and it never reallocates.
- aux: only rows built from a header (OI, PrevClose, MarketStatus, Disconnect from `aux_row_for_non_tick`). These are low volume in Full mode. Pre-sized to 1,024; past that it doubles on a cold path, the same policy as today's ILP buffer past TICK_ROW_BUFFER_PRESIZE_BYTES.
- High-volume aux (out-of-window and connect-snapshot ticks after the close) uses TickRecord tags 2/3, so it costs nothing extra.
Memory: about 6 buffers × 2.5 MiB in normal use, about 49 MiB at the theoretical worst (producer + 4 queued + 4 spares + 2 rescue + 8 parked). Today's ILP buffers reserve 2 MiB each and can grow to 32 MiB each, so this is comparable or lower.

### Drain side

TickWriter::append_tick_into, still on the frame drain:
(1) New `TickRow::validate_parsed_tick(tick)`, split out of from_parsed_tick with identical side effects: the security_id width refusal, the non-finite LTP refusal (same counter, same error! text), and the optional-price non-finite counting via note_non_finite_optional_price on day OHLC and ATP. That is 6 f32 is_finite checks whose branches are never taken, and it keeps tv_tick_optional_price_dropped_total counting refused rows exactly as today, because construction happened before the band/window refusal. from_parsed_tick becomes validate + `TickRow::from_validated` (pure), so every other caller is unchanged.
(2) Compute received_at_ist and ts_ist_nanos with the same row_timestamp_ist_nanos (integer math).
(3) Run the in-band check and session_window::verdict unchanged. A refusal pushes tag OutOfWindowTick through persist_refused_tick: the drain checks i64::try_from(security_id) first, and if that fails it calls the real AuxPacketRow::from_tick on the drain (cold) so the counter and log are unchanged. aux_counters[kind] and aux_rows_appended are bumped at push.
(4) Choose tag Tick or Quote (`to_quotes` and received_at present).
(5) Capacity check `records.len() == records.capacity()`. It is #[cold], should never be reached, and is counted: it runs discard_pending (the width-cap rescue) before the push, so the drain never reallocates and never drops.
(6) Label epoch: one Acquire load of a new candle_contract_labels::LABEL_EPOCH (an AtomicU64 that publish bumps after the ArcSwap store; the line stays Shared in L1, about 1 ns). On the batch's first record or on a change, a #[cold] path takes `load_full()` (an Arc clone, no allocation) and records (record_index, snapshot) in label_switches. Past 4 switches in one batch it keeps the latest and counts it.
(7) Write the record (`*slot = TickRecord{..}`, a straight-line gather from a ParsedTick that is still in L1), then pending += 1, last_capture_seq, note_pending_seq, quote_rows_appended / tick_quotes::note_row, ledger().note_row_appended(arrival for a quote, ts for a tick), tick_ts_placement::note_row. Each is called at the same point, with the same argument and the same Dhan-only gate as today.
Branches per tick: about 15, all predictable. Removed from the drain: the f32→f64 price conversions, the Option assembly, count_nonfinite_tick_floats, the label ArcSwap load and DRAM-cold hash probe, and all ILP text.
offload_flush: unchanged in shape. It moves a RecordBuffer into FlushBatch, try_send, and install_spare_buffer gets a prefaulted RecordBuffer back from the spare lane. The width cap `held >= MAX_PRODUCER_BUFFER_BYTES` becomes `records.len() >= MAX_PRODUCER_RECORDS`; retained_spans is unchanged and remains the bound that fires first in practice (about 1,000 rows per span).
Non-offloaded writers (tests, any pre-split boot flush): flush() calls the same `encode_records_into(&mut self.ilp_scratch, ...)` and then sender.flush. There is ONE append path with no per-row mode branch.

### Writer side

TickWriterSink (the tv-tick-writer thread) gains `encoder: TickRowBufferKind` and `ilp: TickRowBuffer`, pre-sized to TICK_ROW_BUFFER_PRESIZE_BYTES once at split_for_offload and cleared (never shrunk) per batch.
write_inner → `encode_records_into(&mut self.ilp, self.feed, &batch.records)` first, then the existing sender.flush with the same retry and fast-failure window, note_ticks_acked(max_seq), note_ticks_completed, persist_if_due_now, then return_spare_buffer, which now returns the RecordBuffer.
encode_records_into(buf, feed, rb) walks the records in order. It moves to the next label snapshot at each switch index, and the encoders read the label from an explicit `&CandleContractLabels` argument instead of the global. write_tick_line_columns / append_aux_row gain a `labels` parameter; the old global-loading call sites pass `&*candle_contract_labels()`, so nothing else changes. Per tag:
- Tick: row = TickRow::from_validated(&rec.to_parsed_tick(), seq); count_nonfinite_tick_floats → TICK_NONFINITE_COLUMNS_COUNTER; append_within_marker(buf, |b| write_tick_line(b, feed, &row)).
- Quote: the same row, `TickRow{ts_ist_nanos: arrival, ..row}` with exchange_ts = (ltt!=0).then(ltt*1e9), then write_tick_line_into(TICK_QUOTES_TABLE, ...). This is the existing append_quote_row body, made a free fn and shared.
- AuxFromTick(kind): AuxPacketRow::from_tick(kind, &tick, seq), which is guaranteed Some because the drain pre-checked the width, then append_aux_row through the TickRowBuffer::Library/Own match exactly as append_aux does today.
- AuxSide(i): append_aux_row(rb.aux[i]).
An encode Err (unreachable in practice: names are literals, labels are pre-sanitized, but kept honest) rewinds the marker and does what the drain's failure arm does today: note_unapplied(seq), tv_ticks_dropped_total += 1, note_ticks_not_landed(feed, 1), and the HOT-PATH-02 `ilp_append_failed` error throttled at powers of two. batch.rows is decremented so `landed` stays honest.
The same function serves TickRescueSink (its own scratch, created once at split_rescue_offload) and the drain's inline spill fallback (scratch created at split_rescue_offload, used only when the rescue thread is full or gone AND the WAL cannot defer, a path that already does disk I/O).
Writer cost: about 1 ms per 1,000-row batch with the Own encoder (Assumed, from tick_row_append 0.57-0.77 µs per row). At the 12,500 ticks/s opening burst that is about 1.6% of one core.

### Rescue, spill, watermark

Every lifecycle carrier changes only its payload type (TickRowBuffer → RecordBuffer); every field and call order stays as today.
- FlushBatch{records, rows, min_seq, max_seq, unbacked}, plus label_switches inside RecordBuffer.
- RescueBatch{records, rows, min_seq, max_seq, unbacked, floor}.
- parked_rescue: VecDeque<RescueBatch>.
On the drain, unchanged: take_pending_range / restore_pending_range, hold_rescue_floor before a rescue try_send, release_rescue_floor on Full/Disconnected, note_ticks_handed_off on Sent and on park, the H4 park conditions (range.0==0 || unbacked), the wal_defer_check(min,max,unbacked) deferral with note_rescue_outcome_ticks(false)/note_ticks_not_landed/append_dropped/rescue_deferred_to_wal plus its error, and rescue_failure_fate.
Spill files stay ILP text (tick_spill_replay reads them), because each rescuer encodes with encode_records_into before calling the existing perform_tick_rescue / spill_failed_ilp / spill_on_drain. The file bytes are therefore identical, and the curl re-ingest instruction in the log stays true.
On the writer, unchanged: note_ticks_acked(max_seq) only after a clean flush; rescue() → note_rescue_outcome_ticks + note_ticks_not_landed + dropped/spilled counters; note_ticks_completed and floor release at the same points.
Ledger: note_row_appended runs on the drain per accepted row, exactly as today. Every not-landed path (writer spill, rescue failure, WAL defer, and the new writer-side encode failure) calls note_rows_not_landed. So accepted == landed + not_landed holds as it does today; a test asserts the balance under an injected mid-batch encode failure.
Watermark: a row that fails to encode sits inside [min_seq, max_seq], so it is acked with the batch. Today a drain-side append failure inside a range acked by later rows has the same shape, and note_unapplied is what protects both. Behaviour is identical.
Two semantic shifts, both flagged:
(a) The PARKED_RESCUE_MAX_BYTES / rescue_parked_bytes gauge now measures record bytes (RAM actually held), not ILP bytes. The same RAM bound holds about 4x more rows.
(b) The width cap is a record-count bound derived from MAX_ILP_BYTES_PER_RECORD=1024. A test encodes the worst-case row (tick_quotes table, every Option Some, the longest permitted label) and asserts it is ≤1024, which needs a bounded contract-label length (see risks). The QuestDB max_buf wedge margin (MAX_PRODUCER_BUFFER_BYTES*2 ≤ 100 MiB) still holds by construction.
shutdown_residue::OffloadQueue measures rows/unbacked only, so it is unaffected; close_rescue_offload hands parked RecordBuffers over with a blocking send as before.

### Aux, quotes, depth

tick_quotes: same record, tag Quote. The drain still decides the route (tick_quote_route, called by the caller as today) and does the counting (quote_rows_appended, tick_quotes::note_row, ledger keyed on arrival). The writer reproduces the `ts=arrival, exchange_timestamp=LTT` line through the shared write_tick_line_into. Live and replay route identically because routing never moved.
feed_aux_packets: tick-derived aux (OutOfWindowTick, ConnectSnapshot), which is the high-volume kind after the close, uses TickRecord tags 2/3 and the writer calls the unchanged AuxPacketRow::from_tick. Header-derived aux (OI, PrevClose, MarketStatus, Disconnect) still has its AuxPacketRow built on the drain by aux_row_for_non_tick, including the seq refusal. The row is copied into RecordBuffer.aux and an ordering marker record is pushed, so tick/aux interleaving inside a batch is exactly today's and spill files match byte for byte. append_aux's Result contract is kept: it fails only on the cold capacity path, and only after the width-cap rescue has run.
IngestOutcome::WriteFailed becomes reachable only through that cold capacity path. An encode failure is now reported by the writer (same counter, same coded error) and no longer as a drain frame outcome; flagged.
Depth: OUT of PF-4's tick scope, which is a gap in the plan line. append_inline_depth_book (production array_rows) still encodes 2 market_depth_book rows per Full packet on the drain through DepthWriter, and append_inline_depth (10 level rows) does too when array_rows is off. The PF numbers (4.1 µs with book rows, 3.2 µs with own encoder) put the remaining sub-1 µs gap there. Recommend PF-4b: a generic RecordBatch<R> with R = DepthBookRecord (security_id u64, capture_seq i64, ts_nanos i64, segment u8, side u8, kind u8, plus the 100-byte 5-level region as raw [u8;100] or as f32/u32/u16 fields, 128 B total), encoded by DepthWriter's sink through append_book_slots. The plausibility checks and the depth_refused / depth_implausible_kept counters stay on the drain. Same byte-identity proptest shape. Measured as a separate PR.

### Risks

- (Risk) Label timing. Without the epoch switch list, rows straddling a candle_contract_labels publish would take the newer snapshot (NULL → name). The design includes the epoch to stay byte-exact, at about 1 ns/row. The owner may prefer to drop it. A row appended between the ArcSwap store and the epoch bump sees the old snapshot; today that race exists in the same form.
- (Risk) The width-cap bound assumes contract labels are bounded. No maximum label length is enforced today (Unknown). Needs a MAX_CONTRACT_LABEL_BYTES check at publish, or the cap will be derived from an estimate.
- (Risk) Writer CPU rises by about 1 ms per 1,000 rows. If tv-tick-writer is starved (it is not core-pinned), queue_full / width_capped could rise and send more rows to the rescue spill. Watch both counters for one session.
- (Limitation) The encode-failure report moves to the writer thread: IngestOutcome::WriteFailed loses those increments. Same dropped counter and coded error otherwise.
- (Limitation) The parked-bytes gauge now measures record bytes.
- (Limitation) Does not get the drain under 1 µs alone. The inline depth book rows (PF-4b), the shared index (PF-6), the slot layout (PF-7) and per-frame counter batching (PF-8) are still needed.
- (Assumed) Every ns figure until the benches run. Nothing was built or measured for this design.
- (Risk) Proptest scope: the oracle must be the exact current code path, not a re-implementation, or the byte-identity proof is circular. Keep the legacy append fns verbatim under #[cfg(test)] and delete them only once the proptest has been green on main for a release.
- (Rejected alternative) Copying the raw 62-byte packet prefix and re-parsing on the writer saves about 5 ns, but couples the writer to the parser and to any drain-side ParsedTick normalisation. The field-image gather is exact by construction.

## Design

Our prod box can only ever start in ONE AWS data-centre building, and that
building has run out of machines. This plan removes that restriction so the box
can start in whichever of Mumbai's three buildings has space. It costs **₹0/month
extra** and is the only remaining fix — changing the instance type was already
tried on 2026-08-07 and AWS refused for the same reason.

### What an Availability Zone is (plain English)

AWS Mumbai (`ap-south-1`) is three separate data-centre buildings: **1a**, **1b**,
**1c**. Machines live in one building. Capacity is per-building.

Our config says: only ever use building **1a**.

Building 1a is currently full for our machine size. So our box cannot start —
`InsufficientInstanceCapacity`. Buildings 1b and 1c may well have space, but our
own configuration refuses to look.

### The measured evidence

| Fact | Evidence |
|---|---|
| Box unstartable since ~2026-08-06 | 6 start attempts 08:58–10:03 IST on 08-07, all `InsufficientInstanceCapacity` |
| Whole sessions lost | CloudWatch CPU: Aug 3 = 8h, Aug 4 = 5h, **Aug 5 = 0h**, Aug 6 = 7h, **Aug 7 = 0h** |
| Not a budget problem | $2.87 actual vs the $35 ceiling |
| Instance-type change does NOT fix it | `downsize-instance.yml` run 31148235540 tried t4g.medium → **t4g.large** and AWS refused with the SAME error, then rolled back. **1a is out of capacity for BOTH sizes** — so this is an AZ problem, not a size problem. Recorded in the rule file as "do not burn a session on it" |

### Where the pin actually is

`deploy/aws/terraform/main.tf:77` — and it is on the **subnet**, not the instance:

```hcl
resource "aws_subnet" "public" {
  availability_zone = "${var.aws_region}a"   # ← the pin
}
```

The instance inherits the AZ by sitting in that subnet
(`subnet_id = aws_subnet.public.id`, main.tf:351). One subnet in one building
means one possible building, forever.

### Correction to the existing rule-file note

`daily-universe-scope-expansion-2026-05-27.md` says the AZ fix "requires an
instance REPLACEMENT (AZ is fixed at launch) and therefore **a new EIP**."

The replacement half is right. **The new-EIP half appears wrong**: an Elastic IP
in a VPC is **region-scoped**, not AZ-scoped, and can be re-associated with an
instance in any AZ of the same region. So the EIP — and therefore the Dhan
static-IP whitelist — is expected to SURVIVE the move.

Labelled **Assumed**, not Verified: this is from AWS's documented EIP semantics,
not from a live test on our account. Step 0 below verifies it before anything
irreversible happens. If it turns out wrong, the plan still works — it just costs
a new EIP and a Dhan re-whitelist (7-day cooldown), which changes the timing.

### What genuinely does NOT survive

**EBS volumes are AZ-locked.** The 30 GB root volume physically lives in 1a and
cannot be attached to a machine in 1b. Moving buildings means a new volume.

QuestDB data lives on that volume. So the move is snapshot → restore, not
detach → reattach. Snapshots ARE region-scoped, so this works — it is simply the
step that must not be skipped.

### The change

1. **Add subnets in 1b and 1c.** Free, additive, disturbs nothing running.
2. **Snapshot the current root volume** (the rollback artifact).
3. **Recreate the instance** in whichever AZ has capacity, from that snapshot.
4. **Re-associate the EIP** (expected to survive per above).
5. **Rotate the `EC2_INSTANCE_ID` GitHub secret** to the new instance id — every
   deploy/start/stop workflow keys on it and will silently target a dead machine
   otherwise.

Steps 1 and 2 are safe and reversible and can land first. Steps 3–5 are the
disruptive ones and need the operator's go.

## Edge Cases

| Case | Handling |
|---|---|
| 1b AND 1c also out of capacity | Three chances instead of one. If all three refuse, this plan cannot help and the answer is a different instance family — but we would then KNOW that, instead of guessing |
| EIP does not survive the move | Detected at Step 0, before anything irreversible. Falls back to a new EIP + Dhan re-whitelist (7-day cooldown) — a timing change, not a blocker |
| Snapshot restore produces a corrupt/empty volume | Verified BEFORE the old volume is deleted. The old volume is kept until the new box is confirmed healthy |
| The new box comes up with no public IP | The exact 2026-05-31 failure recorded in `variables.tf:61`. Mitigated: the new subnets set `map_public_ip_on_launch = true`, and a fresh launch (unlike the current ENI) honours it. The EIP is the belt-and-braces |
| `EC2_INSTANCE_ID` secret not rotated | Every workflow targets a dead id. Called out as an explicit step, not an afterthought — this is the most likely thing to be forgotten |
| Capacity returns to 1a on its own before we act | Plan still lands: the extra subnets are pure optionality and cost nothing. We stop being one building's outage away from a dead day |
| Operator wants to revert to t4g.medium later | Unaffected — this plan does not touch instance type. It removes the constraint that made the type change look attractive |

## Failure Modes

| Failure | Blast radius | Detection | Response |
|---|---|---|---|
| Terraform apply fails on the new subnets | None — additive resources, nothing detaches | `terraform-apply` workflow red | Fix and re-apply; running box untouched |
| Recreate lands in an AZ that then loses capacity on a later start | Same as today (a dead session) | Start-watchdog alarm | Move to the third AZ; the subnets are already there |
| Snapshot restore loses data | QuestDB history | Row-count comparison before deleting the old volume | Re-restore; old volume still exists |
| EIP re-association fails | Box unreachable — no SSM, no deploys | Reachability check in the runbook | Re-associate manually; the address is held by our account either way |
| Wrong instance id in GitHub secrets | Deploys silently no-op | First deploy after the move | Rotate the secret |
| We move and capacity was never the real cause | Wasted downtime | Box still fails to start | Escalate to AWS support with the capacity errors |

**Not a failure mode:** the token minter. PR #1730 makes token freshness
independent of this box entirely, so even a failed AZ move leaves tokens working.

## Rollback

Every step is reversible, and the irreversible one is fenced by a snapshot.

| Step | Rollback |
|---|---|
| Subnets added | `terraform destroy` on just those resources — nothing was using them |
| Instance recreated | Old root volume is RETAINED (not deleted) until sign-off; relaunch in 1a from it if capacity returns |
| Data restore wrong | Re-restore from the snapshot; the snapshot is kept ~1 week per the 2026-07-15 precedent |
| EIP re-association wrong | Re-associate; the address stays allocated to our account |
| Everything wrong | The box was ALREADY dead before this plan — the floor is the current state, not a working system |

**The honest framing:** the box does not work today. The downside of this plan is
bounded by "still doesn't work", and the upside is that it starts.

## Design

Append `M2 = 21`, `M30 = 22`, `M60 = 23` to `TfIndex` and raise `TF_COUNT` 21 → 24.

**Append, never insert.** The ordinal IS the array index for
`[Mutex<LiveCandleState>; TF_COUNT]` and `[Sender; TF_COUNT]`, **and it is already
written into seal-spill records on disk**. Inserting `M2` at ordinal 2 would
silently re-map every existing spilled record — a 5-minute candle would replay as a
2-minute one. Appending keeps ordinals 0..=20 byte-stable, which is exactly the
pattern the C3 second-scale frames used (`tf_index.rs:75` — *"APPENDED after D1 so
every pre-existing seal-spill ordinal (0..=4) stays byte-stable
(SEAL_SPILL_FORMAT_VERSION stays 1)"*), so `SEAL_SPILL_FORMAT_VERSION` stays **1**
and no on-disk migration exists.

**Bucket seconds:** M2 = 120, M30 = 1800, M60 = 3600. All divide the 22,500-second
session cleanly except M60 (6.25 buckets), which `bars_per_day`'s existing
`div_ceil` already handles — 7 bars, the last one short. Same shape as the existing
M15 (25 bars) and D1.

**Table names:** `candles_2m`, `candles_30m`, `candles_60m` — matching the existing
`candles_<display>` convention.

**The `Tf` (metrics) enum is NOT touched.** `crates/app/src/metrics_catalog.rs`
carries a SEPARATE 9-frame enum (`1m 5m 15m 30m 1h 2h 3h 4h 1d`) whose PR #517
ratchet BANS `"2m"`. Verified independent: the only consumer of `Tf::ALL` is
`crates/app/src/subsystem_memory.rs` (memory accounting), and `TfIndex` already
carries `M3` and `S30` which `Tf` also bans — proving the two are disjoint
namespaces. **Adding M2 to `TfIndex` does not touch the banned `Tf` label set.** If
a future change tries to unify them, that ban must be revisited FIRST with its own
dated note.

**Memory cost:** 3 × 128 B × 25,000 instruments = **9.6 MB**. Negligible against
the r8g.xlarge 32 GiB.

**Row cost:** M2 188 + M30 13 + M60 7 = **208 bars/instrument/day**, ~5.2 M rows/day
at 25,000 instruments — ~11% on top of the existing ~46 M/day sparse estimate.
Inside the ~5,000/sec ingest envelope.

## Rollback

Revert the PR. **Append-only ordinals mean there is no on-disk migration to
undo**: records written while the change was live carry ordinals 21–23, which a
reverted build rejects as out-of-range via the existing `TF_COUNT..=255` loop —
loudly, not silently mis-resolved. Any `candles_2m`/`_30m`/`_60m` tables simply
stop receiving rows; they are never dropped (SEBI retention posture).

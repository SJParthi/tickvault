# Following a tick from capture to the dashboard

**The November 25 daily check found a real discrepancy.** At 15:49 IST the Dhan process reported 67,905,584 accepted buffer writes. The database held 55,744,893 trades and quotes. The saved daily audit and the application log agree on a difference of 12,160,691 after three reads.

| What was checked | Observation | What it establishes |
|---|---|---|
| Production at 17:01 IST | 20,688,491 trades + 35,066,717 quotes = 55,755,208 rows | The database gained 10,315 rows and remained 12,150,376 below the earlier accepted count. The three relevant tables had applied all then-sequenced transactions. |
| Captured frame inventory | The dated archive prefix listed 114 segment objects totaling 7,702,264,423 compressed bytes | The archive has material for reconstruction. Frame and object counts alone cannot identify missing trade or quote keys. |
| Bounded production packet check | Of 24 selected packet positions, 22 had the predicted five-field key. Each of the other two had a byte-identical archived peer with a matching stored key. | The comparison covered stored identities for this sample. Socket-specific suppression and admission for the two positions could not be reconstructed. This sample cannot estimate a full-day loss rate. |
| Local duplicate delivery | Offering the same trade and quote twice produced four accepted writes and two stored rows | Both original keys survived. An aggregate difference can arise through deduplication. The production cause needs independent evidence. |
| Dashboard with the database online | Four submissions for two daily receipts left two rows. A known four-row discrepancy rendered red with the check timestamp and three reads. | The API and browser showed the saved receipt. A direct SQL lookup found the specific daily check. |
| Dashboard with the database offline | On the next refresh after cache expiry, both old rows disappeared and the open dashboard showed “could not read.” | Database unavailability remained visible to the operator. |
| Both storage destinations unavailable | The writer returned an error when a private 128 KiB journal filesystem ran out of space and database writes were refused. The previous journal stayed intact. After space and service returned, the revised producer automatically retried the same receipt after 60.002 seconds. All eleven fields matched in QuestDB. | One producer invocation recovered the new receipt. Replaying the older journal left exactly two rows. A process exit or expiry of the retry window can still interrupt this fallback. |
| Search and restart | A controlled restart preserved all 100,000 synthetic order records and both daily receipts. A separate pair of restart runs each recovered all 2,064 generated receipt rows across their two comparison arms. | This measures persistence through those restarts. The order data in the restart experiment were synthetic. |
| Search speed | Across 400 warmed hits on a known order ID among 100,000 records, p99 was 13.833 ms before restart and 20.529 ms after. | This includes the full loopback HTTP response. Across all 6,000 measured search and dashboard responses in this experiment, zero completed in under one microsecond. |
| In-memory ledger | A hosted run measured 41 ns at p99 on a same-day update, and eight of 49 reported p99 timings exceeded one microsecond. | A constant amount of work to update one counter does not impose a time limit on a database or browser response. |

QuestDB deduplicates trade and quote rows using the timestamp, feed, segment, security ID and capture sequence. To investigate a warning, first read the original daily receipt, then repeat each dated table count and check WAL apply state. To identify an individual missing record, compare the keys of eligible captured market packets with the keys stored for the corresponding interval. Preserve the original audit when later evidence arrives. [Daily warning runbook](../../../error-runbooks/tick-conservation-error-codes.md)

A paired experiment added a bitmap index on correlation ID in a disposable database. Query plans switched to index scans. Tail timings varied between repeated runs. At 100,000 unique IDs the indexed partition took 211.5 MiB more allocated space. No production schema change followed from this experiment.

The Stocks page now retains dated margin-trading eligibility across a refresh. A repeat of the same broker publication preserves its first observation time. Changed terms create a new interval. A refresh without verifiable source data shows unknown from that observation. The producer discards the oldest complete intervals first when the daily file reaches its byte limit. A removed interval can no longer confirm eligibility.
